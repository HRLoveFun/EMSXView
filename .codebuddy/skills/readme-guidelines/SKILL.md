# README 通用内容原则

本 skill 提供一套不绑定具体项目的 README 编写与评审原则，目标是让 README 成为**"读者读完就能正确使用、正确判断、正确贡献"的单一入口文档**。

## 使用时机

- 创建新项目的 README
- 更新或重写既有 README
- 评审 / review README（用户要求"检查 README 质量"、"评审文档"）
- 项目文档结构重组，需要决定哪些信息留在主 README

## 工作流

### 编写或重写 README

1. 阅读完整原则：`references/principles.md`（20 条原则，每条含可操作的检验标准）
2. 先回答四个总纲问题（读者不打开其他文件就能回答）：
   1. **这是什么？**（定位、解决什么问题、面向谁）
   2. **怎么跑起来？**（最短可用的安装与启动路径）
   3. **能做什么、不能做什么？**（能力边界与已知限制）
   4. **出问题去哪查、想贡献怎么改？**（导航与治理）
3. 按读者使用频率降序排布章节，推荐骨架见原则 3
4. 写完后用 `references/principles.md` 末尾的自检清单逐条核对

### 评审既有 README

1. 阅读 `references/principles.md`，重点使用末尾自检清单
2. 逐条核对清单项，输出结构化结果：每项标注"通过 / 不通过 / 不适用"，不通过项给出具体位置与修改建议
3. 优先报告**准确性**问题（无证据的形容词、把规划当现状、隐瞒限制），其次是**结构**问题

## 核心规则速查

以下为最易违反的原则，完整版见 `references/principles.md`：

- **快速开始必须"复制即可运行"**：命令可直接粘贴执行，含前置条件、预期输出与成功判据；占位符必须集中定义（含义 + 默认值 + 覆盖方式），不许读者自行脑补
- **每个形容词都必须可被验证**："高性能""生产级""轻量"要么删除，要么紧跟证据；没有证据的形容词等于噪音
- **能力区分"已实现"与"规划中"**：任何功能清单显式标注状态，规划中的单独成栏
- **已知限制必须主动披露**：不支持的场景、性能天花板、已知缺陷；主动写限制建立信任，隐瞒被发现损失整个项目的可信度
- **单一事实来源**：端口、路径、版本号、环境变量默认值只在权威位置定义一次，其他位置引用；术语全文统一，与代码写法完全一致
- **区分"最后更新"与"最后验证"**：两者都写，"最后验证"写明验证方式
- **降级与失败路径必须公开**：fallback / 重试 / 降级的触发条件、影响范围、用户如何感知；静默降级是数据可信度的头号杀手
- **依赖版本明确**：语言 / 运行时 / 关键库版本写清并说明约束原因；说明 Windows / macOS / Linux 平台差异，或明确声明只支持某一平台
- **配置项表格化**：名称 + 作用 + 默认值 + 是否必填，读者无需读源码即可完成配置
- **测试给出运行方式与覆盖范围**：只说"有测试"不说测什么，等于没测
- **README 纳入变更流程**：影响使用方式的改动必须与代码同一次提交更新 README；"代码改了文档没改"是缺陷而非疏忽
- **三类读者都有入口**：使用者（怎么装怎么用）、贡献者（怎么搭环境跑测试）、评估者（是否成熟活跃），且互不干扰

## 一句话总结

好的 README 不是"介绍项目"，而是"让读者能独立、正确地做决定"。**凡是读者必须靠猜才能继续的地方，都是 README 的缺陷。**
