# README 通用内容原则（完整版）

下面这套原则不绑定任何具体项目，目标是让 README 成为**"读者读完就能正确使用、正确判断、正确贡献"的单一入口文档**。按"读者问题"组织，每个原则都给出可操作的检验标准。

---

## 一、总纲：README 回答四个问题

一份合格的 README，必须让读者在**不打开其他文件**的前提下回答：

1. **这是什么？**（项目定位、解决什么问题、面向谁）
2. **怎么跑起来？**（最短可用的安装与启动路径）
3. **能做什么、不能做什么？**（能力边界与已知限制）
4. **出问题去哪查、想贡献怎么改？**（导航与治理）

**检验标准**：找一个没接触过项目的人，只给 README，看他能否在 10 分钟内跑起最小示例。跑不起来，就是 README 的问题。

---

## 二、开篇原则：一句话定位 + 状态声明

**原则 1：第一屏必须给出"一句话定位"。**
用一句话说清"这是什么、给谁用、核心价值是什么"，不要用营销形容词堆砌。定位之后立刻给出**项目状态**（雏形 / 可用 / 稳定 / 已弃用）与**最近一次验证日期**。

**原则 2：区分"最后更新"与"最后验证"。**
"最后更新"只说明有人动过文件；"最后验证"说明有人确认过内容仍然成立。两者都要写，且写明验证方式。

---

## 三、结构原则：从"最常用"到"最深入"排布

**原则 3：按读者使用频率降序排列章节。**
推荐骨架：
1. 定位与状态
2. 快速开始（最小可运行示例）
3. 安装与依赖
4. 核心用法（覆盖 80% 场景）
5. 能力清单与边界
6. 架构概览（可选，放后）
7. 配置项参考
8. 测试与质量
9. 故障排查
10. 贡献指南与许可

**原则 4：快速开始必须"复制即可运行"。**
所有命令必须可直接粘贴执行，包含必要的前置条件、预期输出、以及"成功长什么样"的判断依据。禁止出现 `<你的路径>` 这类需要读者自行脑补的占位符而不加说明。

---

## 四、准确性原则：可验证，不夸大

**原则 5：每个形容词都必须可被验证。**
"高性能""生产级""企业级""轻量"这类词，要么删除，要么紧跟可验证的证据（基准数据、测试结果、使用案例）。**没有证据的形容词等于噪音。**

**原则 6：能力描述必须区分"已实现"与"规划中"。**
读者最容易被误导的地方，就是把愿景当成现状。任何功能清单都应显式标注状态，规划中的功能单独成栏。

**原则 7：已知限制必须主动披露。**
包括：不支持的使用场景、性能天花板、已知缺陷、平台限制。**主动写限制不会劝退用户，反而建立信任；隐瞒限制一旦被发现，损失的是整个项目的可信度。**

---

## 五、一致性与单一事实来源原则

**原则 8：同一信息只在一处定义，其他地方引用。**
端口、路径、版本号、环境变量默认值等，若在多处重复出现，必然漂移。README 应指定"权威位置"，其他位置只做引用。

**原则 9：术语与命名全文统一。**
同一个概念不要出现多种叫法；若存在历史别名，需在术语表中说明。模块名、命令名、文件名的写法必须与代码完全一致。

**原则 10：占位符必须集中定义。**
若使用 `<X>` 形式的占位符，必须在文首或专门章节给出完整定义表（含义 + 默认值 + 覆盖方式），不能散落各处让读者自行推断。

---

## 六、可复现原则：环境与依赖可重建

**原则 11：依赖必须给出明确版本约束。**
语言版本、运行时版本、关键库版本都要写清，并说明为何需要该约束。避免"最新版即可"这种不可复现的表述。

**原则 12：安装步骤必须覆盖主流平台差异。**
至少在 Windows / macOS / Linux 中说明差异点，或明确声明只支持某一平台。

**原则 13：配置项必须给出"名称 + 作用 + 默认值 + 是否必填"。**
以表格形式呈现，读者无需读源码即可完成配置。

---

## 七、质量与可信度原则

**原则 14：测试必须给出运行方式与覆盖范围。**
写明：测试命令、测试类型（单元/集成/端到端）、是否有覆盖率数据、关键路径是否有回归测试。**只说"有测试"而不说测什么，等于没测。**

**原则 15：降级与失败路径必须公开。**
若系统存在 fallback、重试、降级逻辑，必须说明触发条件、影响范围、用户如何感知。**静默降级是数据可信度的头号杀手。**

**原则 16：版本与变更必须可追溯。**
重大变更应留下摘要与影响范围，而不是只依赖版本控制历史。破坏性变更必须显著标注并提供迁移说明。

---

## 八、可维护原则：README 是活文档

**原则 17：README 必须纳入变更流程。**
任何影响使用方式的改动，都必须在同一次提交中更新 README。**"代码改了文档没改"应当被视为缺陷，而非疏忽。**

**原则 18：避免文档外置造成信息黑洞。**
核心信息（定位、入口、能力、限制、验证方式）必须留在主 README。外置文档只能作为深入补充，且必须给出可点击的准确路径。

**原则 19：控制长度，善用折叠与链接。**
主 README 保持可通读的长度；细节通过链接外置。但链接必须有效、内容必须存在——**死链比没有链接更糟。**

---

## 九、受众原则：为不同读者分层

**原则 20：同时服务三类读者。**
- **使用者**：关心怎么装、怎么用、有什么限制
- **贡献者**：关心怎么搭环境、怎么跑测试、代码规范是什么
- **评估者**：关心项目是否成熟、是否活跃、是否值得依赖

**检验标准**：三类读者都能在 README 中找到自己的入口，且不需要阅读其他读者的内容。

---

## 十、自检清单（可直接用于评审）

发布或更新 README 前，逐条核对：

- [ ] 第一屏能说清"是什么、给谁、什么状态"
- [ ] 快速开始可复制即运行，且有预期输出
- [ ] 所有形容词都有证据支撑
- [ ] 能力清单区分已实现 / 规划中
- [ ] 已知限制被主动披露
- [ ] 端口、路径、版本等关键信息单一事实来源
- [ ] 占位符集中定义
- [ ] 依赖版本明确、平台差异说明
- [ ] 配置项表格化（名称/作用/默认值/必填）
- [ ] 测试命令与覆盖范围明确
- [ ] 降级与失败路径公开
- [ ] 重大变更可追溯
- [ ] 外置文档链接有效且内容存在
- [ ] 三类读者都有清晰入口

---

**一句话总结**：好的 README 不是"介绍项目"，而是"让读者能独立、正确地做决定"。**凡是读者必须靠猜才能继续的地方，都是 README 的缺陷。**
