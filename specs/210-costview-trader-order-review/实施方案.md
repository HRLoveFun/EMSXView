## 0. 结论与先决修正

### 0.1 一句话结论

现有数据足以把交易员视图从「跨市场成本排行」改成「订单级执行复盘台」，但要做三件事：

1. **先修既有口径缺陷**：`Amount` 不是金额、订单参与率求和不可解释、成本符号与计划相反。
2. **按粒度分层**：订单级指标来自 `tca_route_summary`（全量、便宜）；逐笔指标只对当前页/选中订单计算（`processed_fills` + `raw_fills`，单订单毫秒级）。
3. **明确边界**：markout 与盘口深度不做；订单级区间参与率可用；逐桶市场参与率可用 `raw_bdib` 10s bar 在详情页计算（单路由 VWAP 实测与 `par_rate` 比值 1.000）。

### 0.2 先决修正（P0，已确认，独立 PR 先于交易员视图）

#### F1. `Amount` 是委托股数，不是成交金额

**实测证据**（2026-11-03，`D:\db`）：

| 检查 | 结果 |
|---|---|
| `tca_route_summary.Amount == RouteShares` 的路由占比 | 82.55% |
| `Amount == ΣRouteShares` 的订单占比 | 96.9%（194,526 单中 188,497 单） |
| 2026-10 US 路由：`Amount×fx < 10k` 但 `fill×p_avg×fx ≥ 10k` | **6,218 / 7,541 = 82.4%** |
| 2026-10 `Amount` 与 `fill×p_avg` 偏差 >0.5% 的路由 | **24,963 / 24,978 = 99.94%** |
| 样例 NVR US（p_avg=$8,178） | `Amount=10`、`RouteShares=10`、`fill=10`、成交额=$81,780 |

**影响**：

- 异常表「成交金额(本币)」列显示的是股数；`min_notional_usd=10000` 门槛按「股数×汇率」判定，US 近 30 天有 6,218/7,541（82.4%）条路由在金额门槛这一层被错误剔除，异常清单的金额列与门槛同时失真。
- `metric_coverage` 的 `amount_consistency` 探针对比「股数」与「成交额」，恒为 99.94% 不一致；新的全局可信度横幅不得复用它，PR-0a 直接删除该探针。
- 前端 `renderNotional(amount, currency)` 把 `Amount` 渲染成货币，属于同一语义错误。

**修法**：

1. 异常表「成交金额(本币)」改为 `fill × p_avg`；可选增列「委托金额」= `RouteShares × p_avg`；`Amount` 单独显示为「委托股数」。
2. 异常金额门槛改为 `fill × p_avg × fx`；零成交路由按 `RouteShares × p_avg × fx` 计（保持「严重未完成」可见，沿用既有豁免）。
3. **删除** `metric_coverage` 的 `amount_consistency` 探针（其口径把「委托股数」与「成交额」对比，恒误报）；不保留同名指标。`Amount` 语义在 `report_spec` 与 known limitations 写清。订单级 `amount_qty_mismatch` 由交易员视图 §4.12 实现，报告层不再引入股数/金额混用。
4. 更新 `report_spec.REPORT_SPEC["anomaly_notional_gate"]`（同时删除 `amount_consistency_tolerance_pct`）、`SPEC_VERSION`、`docs/report-tca-known-limitations.md`、HTML 文案、异常 CSV 列、`test_report_metrics.py` / `test_monitoring.py` 与 golden 基线。

**验收**：同一日期重跑前后对比；US 近 30 天按 `fill×p_avg×fx<10k` 判定的路由数从 6,266 降到约 51（全量近似）；实际 `throttle.excluded_by_notional` 以异常命中集为准，PR 中必须记录前后值；异常表金额与 `fill×p_avg` 一致；全部测试更新并通过。

#### F2. 订单参与率求和不可解释

**实测证据**：

| 检查 | 结果 |
|---|---|
| 全量 `par_rate > 100%` 路由 | 23,946 / 167,481（14.3%） |
| `par_rate > 200%` / `>1,000%` / `>10,000%` | 20,518 / 10,574 / 2,150 |
| 最大 `par_rate` | 330,459（33,045,900%） |
| 2026-10 按现有 Exchange 分组 par 求和 >100% / >200% | 2,427 / 2,037（共 19,146 组） |
| 其中单路由组 >100% / 多路由组 >100% | 1,571 / 856 |
| 2026-10 单路由订单 par >100% | 1,571 / 16,292（9.6%） |

**根因**：现有 `report_measure.ORDER_PAR_GROUP_COLUMNS` 已按 `(OrderId, order_as_of_date, Exchange)` 分组，跨市场不会相加；问题不在跨市场，而在**同一交易所内多路由并发**——各路由共享同一市场成交量分母，`Σpar_rate` 只在路由时间不重叠时可解释。另一部分是单路由极端值：分母（区间 BDIB 成交量）过小/缺失。现有 `order_par_gt100` 规则把两者混为一谈。

**修法**：

1. 单路由：`par_rate > 1.0` 标 `par_suspect`（warning），`>10.0` 标 critical；进入质量徽章，不直接判「交易差」。
2. 多路由：不再用求和判定；改用 `max(route par_rate)` 与 `par_suspect`，并在报告中披露「多路由参与率不可加总」。
3. 异常规则拆成 `order_par_single_gt100`（仅单路由）与 `route_par_extreme`；`order_par_gt100` 作为兼容键保留一个版本，随后废弃。
4. 保持 `ORDER_PAR_GROUP_COLUMNS` 不变（跨市场分组已是正确口径），只改「组内如何判定」。
5. 同步更新 `report_spec`、异常清单文案、前端规则说明与测试。

**验收**：多路由订单不再因求和进入异常；单路由极端值全部可见；前后计数差异有留档。

#### F3. 成本符号与 bps 换算统一

上游约定（`tca_route_metrics._pnl_in_bps`）：

```text
value = (exec_price / benchmark - 1) × side_sign × 10000
负 = 跑输基准（差），正 = 跑赢基准（优）
```

计划中的公式（如 `side_sign × (vwap - p_arrival)/p_arrival × 10000`）是「正=差」，方向相反。若不统一，所有阈值、提示与排序都会反向。

**修法**：

- 展示与 API 一律使用上游有符号值（负=劣），tooltip 明写「负=成本不利」。
- 规则/提示内部使用 `adverse = -value`（正=差）做比较，避免阈值写成负数。
- 新增前端 `lib/cost-sign.ts` 与后端纯函数 `adverse_bps()`，单测锁定方向。
- 成本分解的 bps 换算统一用 `RouteShares × p_decision` 作分母（与 `wagner_is_bps` 同源），三项之和与 `wagner_is_bps` 闭合；残差是**对账项**，不是「归因不全」。

### 2.3 五个反直觉事实

1. **`Amount` 是委托股数**（§0.2 F1）。凡是把 `Amount` 当金额的展示、门槛与探针，全部要改。
2. **`par_rate` 有大量病态值**（§0.2 F2）。`par_rate` 不能直接作为「交易好坏」的 KPI；必须先标 `par_suspect`。
3. **`order_duration_sec` 不是「订单历时」**。它只是「首笔→末笔成交」的跨度，单笔成交为 NULL。交易员视图应统一叫「成交跨度」，并自己从逐笔计算；不要拿它和「下单到首笔」混用。
4. **同类分位按原计划分组会大面积样本不足**。2026-10 按 `ticker+Side+StrategyType+algo` 取 60 天，peer 中位数仅 6，n≥20 的订单只占 14.7%，n=0 占 11.4%。必须放宽。
5. **延迟长尾主要来自收盘/竞价单的排程**。2026-10 路由级 `route→first fill` 中位 3,041s、p90 21,199s；长尾样例是「前一日 22:32 建单 → 02:46 建路由 → 次日 11:35 伦敦收盘成交」。这不是「释放延迟」，不能计入 p90。

### 2.4 对计划的 5 点修正

| # | 计划假设 | 本仓实际 | 处理 |
|---|---|---|---|
| 1 | 需要从零计算 delay/trading/opportunity/IS | 已物化 `delay_cost`/`trading_cost`/`opportunity_cost`/`wagner_is_bps`，覆盖率 94.3% | 直接复用；只做 bps 换算与对账，不重写公式 |
| 2 | 分时参与率不可得，要降级为日级 | 订单级 `par_rate` 已有；逐桶参与率**可由 `raw_bdib` 10s bar 计算**（单路由 VWAP 实测 `Σfill/Σbar_vol` 与 `par_rate` 比值 1.000） | 保留订单级 `par_rate`；详情页增加逐桶参与率（P1）；`fill_bdib.cum_volume_pct` 本身不可用，改用 `raw_bdib` |
| 3 | `Amount` 偏差 >0.5% 可作质量徽章 | `Amount` 是股数，现有探针 99.94% 误报 | 先修 F1，再改订单级「委托股数一致性」 |
| 4 | peer 分组 = ticker+side+strategy+algo，n<20 不展示 | 该口径 n≥20 仅 14.7% | 两级 peer：精确（ticker+side+algo，180 天，n≥20）+ 宽口径（exchange+side+algo+流动性桶，90 天，n≥50） |
| 5 | 报告里的交易员 tab 可交互 | HTML 报告零 JS、单页静态 | 交互放前端新 tab；HTML 只加静态摘要与横幅 |

## 3. 目标设计

### 3.1 信息架构

```text

│   └─ 完成率桶 · 质量徽章 · 重置 / 查询

│   ├─ 订单数 · 完成率<80% 占比 · 机会成本主导占比

│   ├─ 左：订单列表（服务端排序 + 分页 + 质量徽章）

│       ├─ 算法特征指纹：8 维 peer 分位（n 不足不展示）
```

### 3.8 口径与披露规范

每个替代/代理指标旁边必须有「口径 + 偏差来源」，统一放在 tooltip 与详情卡脚注：

| 指标 | 计算 | 数据源 | 必须披露的偏差 |
|---|---|---|---|
| `completion` | `Σfill / ΣRouteShares` | `tca_route_summary` | 多路由订单按全部路由聚合；成交超委托单独标 overfill |
| `vwap` | `Σ(fill×p_avg) / Σfill` | `tca_route_summary` | `p_avg` 是路由 VWAP；逐笔重算可能略有差异 |
| `arrival_cost_bps` | `(p_avg/p_arrival−1)×side_sign×10000` | `tca_route_summary` | `p_arrival` = 首笔成交前最近 10s bar close；**不含**路由下达→首笔的漂移（该部分在 `delay_cost`） |
| `wagner_is_bps` | `wagner_is / (RouteShares×p_decision) ×10000` | `tca_route_summary` | 与 `arrival_cost_bps` 分母不同，不可直接比大小 |
| `delay/trading/opportunity` | 各自货币成本 ÷ `(RouteShares×p_decision)` ×10000 | `tca_route_summary` | 三项按上游定义闭合到 `wagner_is_bps`；残差 >0.5bps 标「对账异常」 |
| `par_rate` | `fill / 区间市场成交量` | `tca_route_summary` | 分母可能病态（>100% 标 `par_suspect`）；多路由不可加总 |
| 逐桶市场参与率 | `bucket_fill / Σ raw_bdib.volume`（桶内全部 10s bar） | `raw_bdib` | 仅详情页；收盘竞价时段无 bar（US 止于 15:59:50、C1 止于 14:56:50）；多路由按窗口并集，不求和；零成交桶标「休市/无成交」 |
| markout | **不做** | — | 无 L2/中间价；FIX 851 只分类流动性，不提供未来价格；`raw_bdib` bar 价格不足以替代 midquote，含 bar 代理也不做 |
| 被动/主动 | FIX 851（LastLiquidityInd）严格映射 | `raw_fills` | 1=被动、2=主动、4=竞价；3=Routed、0/5/6/Z/空未知；Maker/Taker 映射，P/A 待确认；全量未知 38.01%，必须显示 |
| 订单历时 | 首笔→末笔成交 | `processed_fills` | 单笔成交为 N/A；不等于「下单→完成」；与 `order_duration_sec` 同义但自算 |
| 释放延迟 | 路由创建→首笔连续竞价成交 | `raw_fills` + `route_arrival` | 收盘/竞价单是排程，不是延迟；负值 <1s 视为舍入 |
| 日线区间位置 | `(p_avg−low)/(high−low)` | `raw_bdib` 单日聚合 | 日高低点含订单自身冲击；不是盘口深度 |
| peer 分位 | `rank/(n+1)` | `tca_route_summary` | 口径与窗口必须显示；n<20 不展示 |
| `Amount` | 委托股数 | `tca_route_summary` | **不是金额**；不得用于成交额展示或金额门槛 |

### 4.1 交易员订单复盘台（P0）

**做法**：

- 新 tab `Trader Review`，默认最近 5 个交易日；筛选条覆盖 TraderName、日期、Ticker、Side、StrategyType、Algo、Broker、完成率桶、质量徽章。
- 订单列表**服务端分页/排序**；订单级聚合在 SQL 完成，避免把 20 万路由拉到 Python。
- 多路由订单的筛选语义：**任一路由命中即命中订单**，指标按**全部路由**聚合；列表标 `route_count`；订单头维度（ticker/side/strategy/algo/broker/trader）取**成交股数最大的路由（dominant route）**，多值标 `mixed`，禁止用 `MIN()` 取维度。
- 当前页（≤50 单）再查一次 `processed_fills` + `raw_fills`，补充 `fill_span`、`speed`、`passive_ratio`、`fill_cv`；这些列只对当前页有效，列头标注「当前页」。
- 详情卡右侧展开；支持键盘上下选择、`Esc` 关闭。

**SQL 骨架**：

```sql
WITH matched AS (
  SELECT DISTINCT OrderId, order_as_of_date
  FROM tca_route_summary
  WHERE order_as_of_date BETWEEN ? AND ?
    AND (? IS NULL OR TraderName IN (...))
    AND EXISTS (SELECT 1 FROM tca_route_summary r2
                WHERE r2.OrderId = tca_route_summary.OrderId
                  AND r2.order_as_of_date = tca_route_summary.order_as_of_date
                  AND r2.algo IN (...))   -- 其余维度同理
),
dominant AS (
  SELECT OrderId, order_as_of_date, equ_ticker, Side, StrategyType, algo, Broker, TraderName,
         ROW_NUMBER() OVER (PARTITION BY OrderId, order_as_of_date ORDER BY fill DESC, RouteId) AS rn,
         COUNT(*) OVER (PARTITION BY OrderId, order_as_of_date) AS route_count,
         COUNT(DISTINCT StrategyType) OVER (PARTITION BY OrderId, order_as_of_date) AS n_strategy,
         COUNT(DISTINCT algo) OVER (PARTITION BY OrderId, order_as_of_date) AS n_algo,
         COUNT(DISTINCT Broker) OVER (PARTITION BY OrderId, order_as_of_date) AS n_broker,
         COUNT(DISTINCT TraderName) OVER (PARTITION BY OrderId, order_as_of_date) AS n_trader
  FROM tca_route_summary
),
agg AS (
  SELECT r.OrderId, r.order_as_of_date,
         d.equ_ticker, d.Side AS side, d.StrategyType, d.algo, d.Broker, d.TraderName,
         d.route_count,
         (d.n_strategy > 1 OR d.n_algo > 1 OR d.n_broker > 1 OR d.n_trader > 1) AS mixed,
         SUM(r.fill_count) AS fill_count,
         SUM(r.RouteShares) AS route_shares,
         SUM(r.fill) AS fill,
         SUM(CASE WHEN r.p_avg IS NOT NULL THEN r.fill * r.p_avg END)
           / NULLIF(SUM(CASE WHEN r.p_avg IS NOT NULL THEN r.fill END), 0) AS vwap,
         SUM(r.arrival_cost_bps * r.fill * r.p_avg)
           / NULLIF(SUM(CASE WHEN r.arrival_cost_bps IS NOT NULL THEN r.fill * r.p_avg END), 0) AS arrival_cost_bps,
         SUM(r.opportunity_cost) AS opportunity_cost,
         ...
  FROM tca_route_summary r
  JOIN matched m ON m.OrderId = r.OrderId AND m.order_as_of_date = r.order_as_of_date
  JOIN dominant d ON d.OrderId = r.OrderId AND d.order_as_of_date = r.order_as_of_date AND d.rn = 1
  GROUP BY r.OrderId, r.order_as_of_date
)
SELECT * FROM agg ORDER BY <whitelist> LIMIT ? OFFSET ?;
```

**验收**：

- 同一订单的 `completion` 与 `Σfill/ΣRouteShares` 一致（对 100 单抽样，误差 0）。
- 多路由订单筛选 `broker=A` 时，订单的所有路由都参与聚合（不是只算 A 的路由）。
- 多路由且 `algo`/`broker` 不同：订单头显示 fill 最大路由的维度，`mixed=true`；筛选 `algo=X` 仍命中该订单。
- `vwap` 的分母只含 `p_avg` 非空的 fill；`p_avg` 全空的订单返回 `null`，不返回 0。
- 空结果返回 200 + `total_orders=0`；数据未产出返回结构化 503 `data_not_ready`（沿用现有约定）。

### 4.2 订单执行时间线（P0）

**做法**：

- 上下面板，不用双轴：上为价格线 + 成交气泡（气泡大小 = `FillShares`），下为每桶成交柱 + 累计完成率线；速度/加速度作为下方面板的第二条线或标记，不叠右轴。
- 时间桶默认 5 分钟，可切 15 分钟；桶从首笔成交开始，按固定宽度切；中间无成交的桶补 0（用于速度/加速度），最多 240 桶；超过时自动加宽桶并披露。
- 基准线：`p_decision`、`p_arrival`、`p_avg`、`p_close`、`LimitPrice`；只画非空值，图例标注「首笔前 bar」「决策价」「成交均价」「收盘价」。
- 市场价线：优先用同一 `(equ_ticker, order_as_of_date)` 的 `raw_bdib` 10s bar 聚合到桶（`close` 或桶内 VWAP），成交气泡叠加；`raw_bdib` 缺失时回退 `fill_bdib` 成交时点 bar，并标注「仅成交时点」。
- 逐桶市场参与率：同一批 `raw_bdib` bar 按桶求市场量，`participation = bucket_fill / bucket_market_volume`；收盘竞价桶无 bar 时标 `unavailable`，不画 0%。
- 多路由：每股路由一种颜色；图例显示 `RouteId/Broker/Algo`；参与率分母用订单窗口的**并集**，不把各路由 `par_rate` 相加。

**公式**：

```text
bucket_i = floor((t_i - t_first) / bucket_min)
bucket_fill_i = Σ FillShares in bucket_i
bucket_market_volume_i = Σ raw_bdib.volume in bucket_i
participation_i = bucket_fill_i / bucket_market_volume_i   // volume>0
bucket_speed_i = bucket_fill_i / bucket_min
accel_i = bucket_speed_i - bucket_speed_{i-1}
cum_completion_i = Σ_{j<=i} bucket_fill_j / RouteShares
```

**验收**：

- 桶成交之和 = 订单总成交（误差 0）。
- 最后一个桶的累计完成率 = 订单 `completion`（误差 <1e-6）。
- 单笔成交订单只渲染 1 个桶，速度/加速度显示 N/A，不出现除零。
- 单路由 VWAP 的 `Σbucket_fill / Σbucket_market_volume` 与 `tca_route_summary.par_rate` 比值在 0.99–1.01；差异 >1% 标「窗口/时区差异」。
- 收盘竞价桶显示「不可得（收盘竞价无 bar）」，不显示 0% 参与率。

### 4.3 订单级成本分解条（P0）

**做法**：

- 统一到 bps，分母 `D = RouteShares × p_decision`（与 `wagner_is_bps` 同源）：

```text
delay_bps = delay_cost / D × 10000
trading_bps = trading_cost / D × 10000
opportunity_bps = opportunity_cost / D × 10000
residual_bps = wagner_is_bps - (delay_bps + trading_bps + opportunity_bps)
```

- 堆叠条用 `adverse = -value` 的长度（正=不利），数字标签显示原始有符号值；图例「负=成本不利」。分量为正（成本有利）时用分向条或绿色向左段，不把正负相抵后伪装成单一长度。
- 机会成本在 `completion<1` 时单独高亮；`|opportunity_bps| > |arrival_bps|` 时标「机会成本主导」线索。
- `arrival_cost_bps` 与 `wagner_is_bps` 并列，但 tooltip 写明分母不同：前者相对 `p_arrival`，后者相对 `RouteShares×p_decision`；`arrival` 不含路由下达→首笔的漂移。
- `p_decision` 缺失（5.7%，`RouteShares` 恒有）时：只展示原始货币成本，不画 bps 堆叠，标「IS 分解不可用（无 BDIB/决策价）」。

**验收**：

- 对 100 笔有 `p_decision` 的订单，`|residual_bps| < 0.5`；超过则标「对账异常」，不写「归因不全」。
- 三项 bps 之和与 `wagner_is_bps` 的差 <0.01（浮点容差）。
- `p_decision` 缺失的订单不出现 `NaN` / `Infinity`。

### 4.4 完成轨迹与速度/加速度（P0）

**做法**：

- 从逐笔计算 `fill_span_sec = last_fill - first_fill`；`fill_count<2` → N/A（不是 0）。
- 速度 = `fill / (fill_span_sec/60)`；逐桶速度 = 桶成交量 / 桶分钟。
- `speed_cv = std(非零桶速度) / mean(非零桶速度)`；同时显示零成交桶数，避免「CV 很小但中间长时间不动」的误读。
- `max_speed_ratio = max(非零桶速度) / mean(非零桶速度)`。
- 加速度标记：取 `|accel|` 最大的 2 个桶，标注时刻；不画连续柱状加速度（噪声大）。
- 与价格不利移动对齐：只在有成交时点 bar 的情况下画参考线；不声称是分钟级 markout。

**验收**：

- `fill_count=1` → `fill_span_sec=null`、`speed=null`、`speed_cv=null`，API 不返回 0。
- 桶速度之和 × 桶分钟 = 总成交（误差 0）。
- 零成交桶计入速度序列时，CV 的分母定义在 API 中注明「非零桶」。

### 4.5 单次填充量分布与扫单识别（P1）

**做法**：

- 指标：`fill_median`、`fill_p90`、`fill_cv`、`max_fill_ratio = max(FillShares)/RouteShares`、`top3_fill_share`、`fills_per_min`。
- 只在详情卡展示；列表不占首屏。
- 线索规则：`fill_count>=6 && top3_fill_share>=0.7 && max_fill_ratio>=0.3` → 「集中扫单/切片不均（线索）」；`fill_count<6` 不提示。
- 多路由订单：先按订单合并，再在子表按路由拆分；避免把不同券商的切片混在一起判断。

**验收**：单笔成交不计算 CV/top3（N/A）；`top3_fill_share` 在 `fill_count<3` 时为 N/A。

### 4.6 主动/被动成交拆分与成本差异（P1）

**做法**：

- 逐笔从 `raw_fills` 补 `Liquidity`/`LastCapacity`/`LastMarket`；按 `(OrderId, RouteId, FillId)` 三键连接，覆盖率 100%。
- **按 FIX Tag 851（LastLiquidityInd）严格映射**：`1`=Added Liquidity→被动；`2`=Removed Liquidity→主动；`4`=Auction→竞价；`3`=Routed to Another Exchange→未知；`0`/`5`/`6`/`Z`/`Routed`/空→未知；`Maker`/`Taker` 作为券商扩展映射到被动/主动；`P`/`A` 在业务确认前按未知处理。全量成交股数实测：被动 24.96%、主动 24.54%、竞价 12.49%、未知 38.01%；按算法 VWAP 可分类约 61%、POV 约 80%、CLOSE 仅约 13%（其余为竞价）。UI 对 `3/0/5/6/Z/P/A` 标「映射待业务确认」，不阻塞 `1/2/4` 的使用。
- 未知占比 = 未识别成交股数 / 总成交股数；>10% 在订单卡与 KPI 上打 `liquidity_unknown` 徽章。
- 成本差：

```text
passive_vwap = Σ(FillShares×FillPrice | passive) / Σ(FillShares | passive)
passive_cost_bps = (passive_vwap/p_arrival - 1) × side_sign × 10000
aggressive_cost_bps 同理
diff = passive_cost_bps - aggressive_cost_bps   // 负=被动更差
```

- `LastCapacity`/`LastMarket` 只做分布展示，不用于分类；`Auction` 单独一档，不计入被动/主动。

**验收**：

- `passive + aggressive + unknown = fill`（按股数，误差 0）。
- 未知占比 >10% 时页面有明确徽章；不允许只显示被动占比而不显示未知。
- 映射变更只改一个常量表；单测覆盖 FIX 851 的 `1/2/3/4/0/5/6/Z/空` 与 `Maker/Taker/P/A/Auction/Routed` 全部取值。

### 4.7 算法特征指纹与同类分位（P1）

**做法**：

- 8 维：`completion`、`duration`、`speed`、`fill_cv`、`passive_ratio`、`avg_fill/RouteShares`、`arrival_cost_bps`、`opportunity_cost_bps`。
- 两级 peer：
  1. **精确同类**：`equ_ticker + Side + algo`，近 180 天，n≥20 → 分位；
  2. **宽口径**：`Exchange + Side + algo + ADV20 分位桶`，近 90 天，n≥50 → 分位，标注「宽口径」；
  3. 都不满足 → 「样本不足」，只显示原值与 n。
- 分位公式：`p = (count(peer < x) + 0.5×count(peer = x)) / n`；`z = (x−median)/MAD`，MAD=0 时用 `IQR/1.349`，仍为 0 则不给 z。
- 展示：横向分位条（0–100），中位 50 参考线；不用雷达图（8 维雷达在窄卡片里不可读）。
- `fingerprint_deviation = count(|p−0.5|>0.4)`，作为「偏离维度数」线索，不直接判好坏。

**验收**：

- n<20 时 API 不返回 `percentile`（返回 `null` + `sample_insufficient=true`）。
- 任一维度为 null（如单笔成交的 speed、无 `Liquidity` 的 passive_ratio）时该维度不计算分位，显示 N/A；禁止把 null 当 0。
- 分位方向：成本类「分位越低越差」在 tooltip 说明；完成率类「分位越低越差」。
- 同一订单重复请求结果稳定（peer 窗口固定，缓存 key 含数据最新日期）。

### 4.8 条件化改进提示规则引擎（P1）

**规则表**（内部用 `adverse = -value`，正=差）：

| ID | 条件 | 证据 | 置信度 | 展示 |
|---|---|---|---|---|
| H1 机会成本主导 | `completion<0.8` 且 `adverse(opp_bps)>peer_p75(adverse(opp_bps))` 且 `adverse(opp_bps)>adverse(arrival_bps)` | 完成率、机会成本、peer p75、n | n≥50 高 / n≥20 中 / 否则低 | 「复核未成交原因」 |
| H2 被动逆向选择 | `recognized_share≥0.8` 且 `passive_ratio≥0.6` 且 `adverse(passive_cost_bps)>median(adverse(passive_cost_bps))+2×MAD` | 被动占比、被动成本、peer 中位/MAD、n | 同上 | 「复核被动成交时点」 |
| H4 释放延迟 | `algo∈{vwap,pov,twap}` 且 `route_to_first_continuous_fill>peer_p90(route_to_first_continuous_fill)` 且 `>60s` | 延迟、peer p90、n | n≥20 | 「复核路由下达→首笔」 |
| H5 尾盘未完成 | `completion<0.95` 且 `unfilled>0` 且末笔在收盘前 30 分钟内 | 完成率、未成交、末笔时刻 | n≥10 | 「复核尾盘流动性」 |
| H6 集中扫单 | `fill_count≥6` 且 `top3_share≥0.7` 且 `max_fill_ratio≥0.3` | 填充分布 | 自身样本 | 「线索：切片不均」 |
| H7 单笔成交 | `fill_count≤1` 且 `completion<0.95` | 填充笔数 | 自身样本 | 「单笔成交，节奏不可评估」 |

> H2 要求 `recognized_share≥0.8`；FIX 851 全量可分类率约 49.5%，VWAP 约 61%、POV 约 80%、CLOSE 约 13%。因此 H2 只在高识别率订单触发；未知 >20% 时置信度降为 low，且不展示「被动占比」结论。

**不做**：H3「不利区间加速」需要成交前后的连续**报价**；`raw_bdib` 虽有连续 10s bar，但只有成交价（`close`/`vwap`）、无 bid/ask，无法区分「价格不利移动」与订单自身冲击，`fill_bdib` 则只有成交时点 bar。留到上游提供 L2/quote（或逐笔报价）后再做，本期不提供伪实现。

**输出约束**：

- 每条提示必须带 `rule_id`、`evidence`（具体数值）、`peer_n`、`confidence`；缺一项不渲染。
- 提示语气是「线索/需复核」，不写「应该用 X 算法」。
- `quality.level=bad`（overfill / cost_missing）时抑制成本类提示，避免在坏数据上给建议。

**验收**：每条规则有正/反例单测；符号方向错误能被测试捕获；n 不足时规则不触发。

### 4.9 延迟分解（P1）

**做法**：

- 复用 `CostView/src/monitoring/route_arrival.py`（DL-12）：
  - `p_route_arrival` 与 `algo_latency_sec` 优先取上游物化列；没有则 L2 自给（`raw_bdib` 单 ticker/日）。
- 三段：

```text
order_to_route_sec = NyTranCreateAsOfDateTime - NyOrderCreateAsOfDateTime
route_to_first_fill_sec = MIN(DateTimeOfFill) - NyTranCreateAsOfDateTime
order_to_first_fill_sec = order_to_route_sec + route_to_first_fill_sec
```

- 时区：`raw_fills` 的 NY 时间用 `data_access/common/exchange_tz.py` 转交易所本地；与 `processed_fills.exchange_exec_time` 交叉核对。
- **收盘/竞价单**：`algo=close` 或首笔 `is_closing_auction=1` → `scheduled=true`，显示「按计划在收盘竞价成交」，不计入 `release_delay_p90`。
- **连续算法**：用首笔**非竞价**成交计算 `first_continuous_fill_sec`；负值 <1s 视为舍入，钳到 0；<−1s 标 `latency_anomaly`。
- 展示：三段横向条形 + 订单值 + peer p90；标注「交易员/系统段」与「券商算法段」，不写「可控」（无法证明）。

**验收**：

- 2026-10 的收盘单不再进入 p90；p90 的样本量与覆盖率随卡显示。
- 负延迟 <1s 不出现在告警；<−1s 有徽章。
- `trader_delay_cost + algo_delay_cost ≈ delay_cost`（有 `p_route_arrival` 时，误差 <1%）。

### 4.10 日线行情辅助（P2）

**做法**：

- 订单级常用指标从 `bdib_daily_summary` 取：`daily_close`、`daily_vwap`、`adv_20d`、`total_volume`、`daily_volatility`。
- 日高低/开盘从 `raw_bdib` 单 ticker/日聚合（实测 2,340 根 bar，12ms）；只在详情卡按需查询，不进列表。
- 指标：

```text
range_position = clamp((p_avg - low) / (high - low), 0, 1)
daily_range_bps = (high - low) / daily_vwap × 10000
vwap_vs_close_bps = (p_avg/daily_close - 1) × side_sign × 10000   // 负=劣
adv20_quartile = 同市场 ADV20 四分位
```

- 展示：`low — vwap — high` 位置条；ADV 分位徽章；日振幅标签。
- 披露：日高低含订单自身冲击；不是盘口深度；不用于分时参与率或 markout。

**验收**：`high=low` 或 `daily_vwap=0` 时返回 `null`；不出现除零；详情卡不因单 ticker 无 `raw_bdib` 而整体失败（降级为「日线不可得」）。

### 4.11 异常清单与订单卡联动（P2）

**做法**：

### 4.12 数据质量徽章与全局可信度横幅（P0）

**订单徽章**：

| 徽章 | 级别 | 条件 | 影响的展示 |
|---|---|---|---|
| `overfill` | bad | `fill > RouteShares` | 完成率、机会成本不可信 |
| `amount_qty_mismatch` | warn | 订单级 `|Amount − ΣRouteShares| / max(Amount,1) > 0.5%` | 委托股数口径 |
| `cost_missing` | warn | `arrival/opportunity/wagner` 任一为 NULL | 成本分解不可用 |
| `par_suspect` | warn/bad | 单路由 `par_rate>1`（>10 为 bad）；多路由只看 `max(route par)` | 参与率 |
| `liquidity_unknown` | info/warn | 未知 `Liquidity` 股数占比 >10% | 被动占比 |
| `single_fill` | info | `fill_count<2` | 速度/加速度 N/A |

**全局横幅（始终显示，不因 0 触发而隐藏）**：

| 检查 | 口径 | 影响 KPI |

**验收**：4 类检查在空数据、单日、跨年、超大范围四种情况下都能渲染；没有「条件隐藏」；`Liquidity` 未检查时明确写「未检查」。

### 4.15 逐桶市场参与率（P1，详情）

**做法**：

- 选中订单详情按 `(equ_ticker, order_as_of_date)` 读 `raw_bdib` 的 10s bar（US 2,340 根、C1 1,423 根；单次约 12ms），按 5/15 分钟桶求和 `volume`。
- `participation_i = bucket_fill_i / bucket_market_volume_i`；桶内无 bar 或 volume=0 时状态为 `market_closed` / `no_market_volume`，不画 0%。
- 单路由订单：`Σfill / Σmarket_volume` 应与 `tca_route_summary.par_rate` 一致。实测 5 笔单路由 VWAP（NNEUR、ULTA、SAN、GS、STLD）比值为 1.000、1.000、0.990、1.000、1.000。
- 多路由订单：分母取各路由时间窗口的**并集**；禁止把各路由 `par_rate` 相加（并发路由共享市场量）。
- 收盘/竞价单：US `raw_bdib` 止于 15:59:50、C1 止于 14:56:50，收盘竞价段无 bar；该桶标「不可得」，不参与订单级 `par_rate` 对账。
- 缓存按 `(ticker, date)`，TTL 10 分钟；同一页多单共享缓存。

**披露**：10s bar 的 lit 成交量，不含场外/暗池全量；无盘口深度、无分 venue；收盘竞价段缺失；零成交桶不等于 0% 参与率。

**验收**：单路由 VWAP 对账比值 0.99–1.01；所有缺口状态可见；详情页单次 <100ms（缓存命中）。

### 4.16 markout（不做）

2026-11-03 确认：**本期不做 markout，包括 bar-close/VWAP 代理**。

- FIX Tag 851（`Liquidity`/LastLiquidityInd）只分类「添加/移除流动性、竞价、被路由」，不提供成交后的价格路径；它不是 markout 的数据源。
- 真 markout 需要成交时点与 5/15/30 分钟后的 bid/ask/mid；当前没有 L2/quote，`raw_bdib` 的 10s bar 只有成交价（`close`/VWAP），不能替代 midquote。
- 2026-10 抽样（48 组 ticker/date、3,522 笔成交）显示：bar 代理分市场覆盖 54–99%、陈旧 0.3–67%，`close` 与单根 bar VWAP 平均差 0.4–8.3bps、符号一致 92.5–99.8%；代理选择本身就会改变结论，不能承担 KPI/排名。
- 因此不新增 `MarkoutPanel`、不加 API 字段、不进 KPI/peer/导出；后续若上游补 L2/quote，再按「目标时刻后 60 秒内 midquote + 覆盖/陈旧门槛」重新立项。

### 7.3 复核结论（2026-11-03 追问）

#### 7.3.1 markout：已确认不做

- FIX Tag 851（`Liquidity`/LastLiquidityInd）只分类「添加/移除流动性、竞价、被路由」，不提供成交后的价格路径；它不是 markout 的数据源。
- 真 markout 需要成交时点与 5/15/30 分钟后的 bid/ask/mid；当前没有 L2/quote。
- `raw_bdib` 10s bar 只能做 bar-close/VWAP 代理；2026-10 抽样（48 组 ticker/date、3,522 笔成交）覆盖 54–99%、陈旧 0.3–67%、`close` 与 VWAP 差 0.4–8.3bps、符号一致 92.5–99.8%。代理选择本身就会改变结论，不能承担 KPI/排名。
- 结论：**本期不做 markout（含 bar 代理）**，不进 API/KPI/peer/导出；若后续上游补 L2/quote，再按「目标时刻后 60 秒内 midquote + 覆盖/陈旧门槛」重新立项。
- FIX 851 只用于被动/主动拆分：`1/2/4` 有标准语义；全量股数被动 24.96% + 主动 24.54% + 竞价 12.49%，未知 38.01%，必须披露。

#### 7.3.2 逐桶市场参与率：可做，详情级 P1

**结论：可做，之前的「不可得」判断是错的。**

- `fill_bdib.cum_volume_pct` 只累计「有成交的 bar」，不能当区间市场量；但 `raw_bdib` 有完整 10s bar 的 `volume`。按 `(equ_ticker, order_as_of_date)` 读当日 bar，按 5/15 分钟桶求和即可。
- 单路由 VWAP 实测（NNEUR、ULTA、SAN、GS、STLD）：`Σfill / Σmarket_volume` 与 `tca_route_summary.par_rate` 的比值为 1.000、1.000、0.990、1.000、1.000；桶参与率中位数 0.13%–2.04%，符合直觉。
- 限制：US `raw_bdib` 止于 15:59:50、C1 止于 14:56:50，收盘竞价段无 bar；多路由必须用窗口并集，不能求和；零成交桶标「休市/无成交」而不是 0%。
- 性能：单 ticker/日 2,340 根 bar、约 12ms；详情页单次查询可接受，按 `(ticker,date)` 缓存。

### 7.4 明确不做

- 不做 markout（含 bar-close/VWAP 代理；无 L2/中间价）。
- 不做盘口深度、队列位置、撤单率。
- 不做算法推荐结论（只给线索与证据）。
- 不做自动改单/路由/提交（ExecutionView 职责）。
- 不做跨交易员排行榜（本期只做筛选与复盘；排行榜需单独评估隐私与样本）。
- 不做实时/盘中止损（CostView 盘后只读）。

### B. 公式与符号

```text
# 上游符号：负=劣
arrival_cost_bps = (p_avg / p_arrival - 1) × side_sign × 10000
wagner_is_bps   = wagner_is / (RouteShares × p_decision) × 10000
delay_bps       = delay_cost / (RouteShares × p_decision) × 10000
trading_bps     = trading_cost / (RouteShares × p_decision) × 10000
opportunity_bps = opportunity_cost / (RouteShares × p_decision) × 10000
residual_bps    = wagner_is_bps - (delay_bps + trading_bps + opportunity_bps)

# 提示/阈值内部：正=劣
adverse(x) = -x

# 分位
p = (count(peer < x) + 0.5 × count(peer = x)) / n
z = (x - median) / MAD;  MAD = median(|x - median|)

# 完成/速度
completion = Σfill / ΣRouteShares
fill_span_sec = last_fill - first_fill
speed = fill / (fill_span_sec / 60)
bucket_speed = bucket_fill / bucket_min
accel = bucket_speed_i - bucket_speed_{i-1}

# 逐桶市场参与率（详情；分母用订单窗口并集）
bucket_market_volume_i = Σ raw_bdib.volume in bucket_i
participation_i = bucket_fill_i / bucket_market_volume_i
order_participation = Σfill / Σmarket_volume   // 与 par_rate 对账
```
