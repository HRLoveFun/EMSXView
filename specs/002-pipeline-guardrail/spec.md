## Clarifications

### Session 2026-06-16

- Q: 阶段间变更影响检测策略——代码修改后如何确保不产生跨阶段的语义性副作用（"改了A处影响B处"）？ → A: 变更时自动运行受影响阶段及其下游的全链路对比测试（对比基线输出）
- Q: 护栏机制触发节点——在开发工作流的哪个阶段触发护栏检查以尽早发现"改了A处没改B处"？ → A: CI 预检阶段触发（代码提交/PR 时自动运行管道完整性测试和基线对比）
- Q: 阶段间数据契约兼容性策略——当开发者修改某阶段输出字段时，如何防止下游阶段静默失败？ → A: 严格契约校验：阶段输出模式变更时自动校验所有下游阶段的输入期望是否仍满足，不满足则拒绝变更
- Q: 异常严重等级与升级策略——不同严重程度的异常应触发不同的阻断和响应行为？ → A: 三级分类：Info（记录可恢复异常，不阻断）、Error（阻断当前阶段，不熔断下游）、Critical（立即熔断全链路并告警）
- Q: 测试基线快照的建立与更新策略——基线数据如何创建和更新以防止频繁误报？ → A: 手动评审更新：基线差异需在 Code Review 中由 Reviewer 确认后归档为新基线，防止未经审查的基线漂移
- Q: 数据校验切入位置——实际管道以数据库表为阶段间中介（非内存记录流），校验应放在哪里？ → A: 阶段写 DB 后立即对写入数据执行校验，下游阶段读 DB 前对输入数据执行预检（保持 DB 中介模式）
- Q: 护栏机制与现有代码的集成方式——PipelineContext 已有基础错误追踪，如何在不膨胀现有类的前提下叠加分级熔断、运行 ID、校验钩子？ → A: 独立护栏编排层（GuardPipeline 包装 FinancialPipeline），PipelineContext 零改动，所有 stage 签名不变
- Q: S1 与 S2-S10 的差异化处理——S1 处理外部数据摄入，S2-S10 处理内部 DB 加工，是否应区别对待？ → A: 区分外部入口与内部加工：S1 使用宽松校验+重试降级策略，S2-S10 使用严格校验+按严重等级熔断
- Q: 可选阶段的护栏行为——被跳过的阶段（如 skip_ingest/skip_bdib）应如何处理？ → A: 跳过不计数：被跳过的阶段完全排除在护栏之外，不执行校验、不计入熔断统计、不影响管道运行状态

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管道节点数据校验 (Priority: P1)

作为数据工程师，当我修改管道中某一阶段的处理逻辑时，我需要确保该阶段的输出数据仍然符合下游阶段的预期格式和约束，以防止错误数据流入后续节点并造成级联故障。

**Why this priority**: 数据完整性是管道的基础保障。若上游输出产生不合规数据而未被拦截，下游所有阶段都会受影响，且追溯根因极其困难。这是护栏机制的核心价值所在。

**Independent Test**: 向某管道阶段输入包含缺失必填字段、错误类型或越界值的记录，验证系统能在该阶段输出边界处拦截并报告具体不合规项。无需部署其他护栏组件即可验证。

**Acceptance Scenarios**:

1. **Given** 管道某阶段输出数据包含缺失必填字段的记录，**When** 数据通过阶段输出校验点，**Then** 系统拒绝该记录通过，记录校验失败日志（包含字段名、期望类型、实际值），并阻止该数据流入下游阶段
2. **Given** 管道某阶段输出数据中某数值字段超出合理范围（如成交量为负值），**When** 数据通过阶段输出校验点，**Then** 系统识别为约束违规，拒绝通过并生成告警日志
3. **Given** 管道某阶段输出数据完全符合模式定义，**When** 数据通过阶段输出校验点，**Then** 所有记录正常通过，系统记录校验通过摘要（总记录数、通过数）
4. **Given** 阶段处理完成后产生空数据集，**When** 数据到达输出校验点，**Then** 系统根据配置决定是否接受空数据集（默认拒绝），并记录相应日志

### User Story 2 - 管道异常熔断与告警 (Priority: P2)

作为运维人员，当管道运行过程中出现异常（如数据校验失败率超过阈值、阶段执行超时、外部数据源不可用），我希望系统能自动阻断后续阶段的执行并发出告警通知，以防止错误扩散并让我第一时间介入处理。

**Why this priority**: 熔断机制防止局部故障演变为全链路故障。在数据校验（P1）到位后，熔断是错误扩散的最后一道防线，确保"坏数据不过夜"。

**Independent Test**: 模拟一个管道阶段连续多次校验失败，验证系统自动停止后续阶段执行并触发告警。可独立于 P1 的校验规则测试熔断逻辑。

**Acceptance Scenarios**:

1. **Given** 管道某阶段连续 N 次执行均出现校验失败（失败率超过配置阈值），**When** 第 N+1 次执行触发时，**Then** 系统自动熔断该阶段及所有下游阶段，记录熔断事件（触发原因、时间、影响范围），并发送告警通知
2. **Given** 管道阶段执行超过预设时间阈值，**When** 超时发生，**Then** 系统记录超时事件，将该阶段标记为异常，并在一定条件下触发后续阶段熔断
3. **Given** 熔断状态已激活，**When** 运维人员确认问题已修复并手动重置熔断状态，**Then** 系统恢复正常管道调度，从断点或指定起始阶段继续执行
4. **Given** 外部数据源（如 Bloomberg API）不可用，**When** 数据拉取阶段尝试连接失败并达到重试上限，**Then** 系统记录连接故障，触发熔断并发送告警

---

### User Story 3 - 管道完整性自动化测试 (Priority: P1)

作为开发者，当我修改管道代码（重构、新增功能、修复 Bug）并提交 Pull Request 时，CI 预检应自动运行管道完整性测试和基线对比，以确保我的改动没有意外破坏管道的任何环节（包括直接影响的下游阶段）。

**Why this priority**: 自动化测试是护栏机制的"主动防御"层，与数据校验（被动拦截）同等重要。没有自动化测试，每次代码变更都是一次赌博。P1 级别确保在数据校验（另一个 P1）完成后立即获得验收能力。

**Independent Test**: 运行测试套件，使用已知的测试数据从头到尾执行完整的管道流程，验证每个阶段的输出是否符合预期。可独立于生产数据和真实外部 API 运行（使用 Mock 数据）。

**Acceptance Scenarios**:

1. **Given** 管道代码发生修改，**When** 开发者运行管道完整性测试套件，**Then** 所有核心数据流转路径的测试用例被执行，结果清晰显示通过/失败
2. **Given** 某阶段处理逻辑被意外修改导致输出格式变化，**When** 运行该阶段及其下游阶段的端到端测试，**Then** 测试失败并明确指出输出与预期的差异（字段缺失、类型不匹配、值偏差），且下游受影响阶段同步报错
3. **Given** 新增一个管道阶段，**When** 为该阶段编写并运行测试用例，**Then** 测试覆盖该阶段的输入边界、正常处理路径和异常处理路径
4. **Given** 测试套件执行完成，**When** 查看测试报告，**Then** 报告包含每个阶段的覆盖率统计和执行耗时
5. **Given** 某阶段代码发生修改（如算法参数调整），**When** 系统检测到变更后自动运行该阶段及所有下游阶段的全链路对比测试，**Then** 对比当前输出与基线快照的差异，差异超过阈值则标记为失败并明确指出偏差阶段和数据字段

---

### User Story 4 - 数据流转日志追踪 (Priority: P2)

作为数据分析师或运维人员，当管道运行出现异常或结果数据可疑时，我需要通过日志追踪数据的完整流转路径，定位异常发生的具体节点和影响范围。

**Why this priority**: 日志是问题排查的最终手段。当校验拦截或熔断触发后，运维人员需要日志来理解"发生了什么"。没有结构化日志，P1 和 P2 的告警将缺乏可操作性。

**Independent Test**: 执行一次管道运行后，检查日志输出是否包含每个阶段的入口/出口摘要、数据量统计、执行耗时、以及异常记录（若有）。可独立于校验和熔断机制验证日志完整性。

**Acceptance Scenarios**:

1. **Given** 管道从采集到分析完整执行，**When** 查看管道日志，**Then** 日志按阶段顺序记录每个节点的开始时间、结束时间、输入记录数、输出记录数、校验通过/失败数
2. **Given** 某阶段处理发生异常，**When** 查看该阶段的日志，**Then** 日志包含异常类型、异常消息、异常发生的具体数据上下文（记录 ID 或行号）、堆栈跟踪
3. **Given** 管道运行完成，**When** 查看概要日志，**Then** 日志包含整条管道的总执行时长、各阶段耗时占比、数据流经各阶段的记录数变化
4. **Given** 多次管道执行历史，**When** 查询特定期日或批次日志，**Then** 能按日期和批次号检索对应的完整管道运行日志

### Edge Cases

- 管道在中间阶段被熔断中断后，已处理的数据应保持一致性——部分提交或回滚策略？[见 Assumptions]
- 某阶段校验通过但数据语义错误（如成交价格正确但不合理）时，校验规则能否覆盖业务语义？→ 校验层仅保证数据格式和值域正确性；业务语义异常（如偏离历史均值 3σ 的成交价）由下游分析阶段（S8-S10）通过统计异常检测覆盖，不在护栏校验范围内
- 并发执行同一管道不同日期的任务时，熔断状态如何隔离（按日期？按管道实例？）
- 日志存储空间无限增长时的归档策略？
- 外部数据源返回部分成功部分失败时（如 Bloomberg 返回 80% 数据），如何处理？
- 校验规则本身有 Bug 导致正常数据被误拦截时的回退机制？→ FR-024：运维可通过 `GUARDRAIL_VALIDATION_BYPASS_ON_ERROR` 配置项启用降级模式，校验失败不拒绝入库，改为记录 WARNING 日志后放行
- 上游阶段输出模式变更后，下游阶段消费代码尚未同步更新时的过渡期如何处理？

## Requirements *(mandatory)*

### Functional Requirements

#### 数据校验与模式检查

- **FR-001**: 系统 MUST 在每个管道阶段将数据写入数据库后立即对写入数据执行模式校验，校验内容包括：必填字段完整性、字段数据类型、字段值域范围（如非负约束、枚举值约束）；校验不通过的数据 MUST NOT 持久化入库
- **FR-002**: 系统 MUST 支持以声明式方式定义每个阶段的输入/输出数据模式，模式定义 MUST 与处理逻辑分离；输出模式变更时 MUST 自动校验所有下游阶段的输入期望是否仍满足，不满足则拒绝变更并列出受影响的阶段和字段
- **FR-003**: 校验失败时，系统 MUST 记录具体违规记录的位置（行号或主键）、违规字段名、期望约束与实际值
- **FR-004**: 系统 MUST 支持按校验违规的严重等级配置不同的处理策略：Info 级不影响流程执行（仅记录日志），Error 级阻断当前阶段但不熔断下游，Critical 级立即熔断全链路并告警；S1（外部数据摄入阶段）采用独立宽松策略（重试降级而非熔断），S2-S10（内部加工阶段）采用标准严格策略
- **FR-005**: 系统 MUST 在每个阶段从数据库读取输入数据后、开始处理前执行输入数据预检，确认数据格式和必填字段符合预期；S1 阶段预检对象为外部数据源（非数据库）；被配置跳过的阶段（如 skip_ingest/skip_bdib）完全排除在护栏之外，不执行校验、不计入熔断统计；各阶段的校验策略（宽松/严格）遵循 FR-004 的分化定义

#### 异常捕获与熔断机制

- **FR-006**: 系统 MUST 追踪每个管道阶段的执行状态（成功/失败/超时/校验失败），并维护阶段级别的健康状态，附带异常严重等级（Info/Error/Critical）
- **FR-007**: 系统 MUST 支持按严重等级配置熔断触发条件：Critical 级异常立即触发全链路熔断，Error 级异常在达到连续失败次数或失败率阈值后触发阶段阻塞
- **FR-008**: 当熔断条件满足时，系统 MUST 自动阻止当前阶段及所有下游阶段的执行
- **FR-009**: 系统 MUST 在熔断触发时发送告警通知（至少支持日志记录告警，可选支持外部通知渠道）
- **FR-010**: 系统 MUST 支持运维人员手动重置熔断状态，重置后可指定从断点或指定阶段恢复执行
- **FR-011**: 系统 MUST 为外部依赖调用（如 Bloomberg API、数据库连接）实现重试机制，支持配置重试次数和退避策略

#### 自动化测试用例

- **FR-012**: 系统 MUST 提供针对每个管道阶段的独立单元测试，使用可控的测试数据验证阶段的输入-输出转换正确性
- **FR-013**: 系统 MUST 提供端到端集成测试，覆盖从数据采集到最终输出的完整核心流转路径
- **FR-014**: 测试用例 MUST 包含正常路径、边界值（空数据、单条记录、大批量数据）和异常路径（字段缺失、类型错误）三类场景
- **FR-015**: 测试套件 MUST 支持独立运行（不依赖真实 Bloomberg API 或外部数据库），使用 Mock/Fixture 数据
- **FR-016**: 测试执行结果 MUST 输出结构化报告，包含每个阶段的测试通过率、覆盖率和执行耗时
- **FR-022**: 系统 MUST 支持为每个阶段的关键输出建立基线快照，代码变更后自动运行受影响阶段及其下游阶段的全链路对比测试，差异超过配置阈值时标记为失败；基线更新 MUST 经过 Code Review 人工确认后方可归档，防止未经审查的基线漂移
- **FR-023**: 管道完整性测试和基线对比 MUST 集成到 CI 流水线中，在代码提交或 Pull Request 时自动触发，测试未通过时阻止代码合并

#### 运维保障

- **FR-024**: 系统 MUST 提供校验规则紧急降级开关（配置项 `GUARDRAIL_VALIDATION_BYPASS_ON_ERROR`），当校验规则自身异常导致正常数据被误拦截时，运维人员可启用降级模式：校验不通过的数据不再被强制拒绝，改为记录 WARNING 日志后放行；降级模式仅影响校验拦截行为，不影响熔断和日志记录

#### 日志记录

- **FR-017**: 系统 MUST 为每次管道执行生成唯一运行 ID，所有日志记录 MUST 关联该运行 ID
- **FR-018**: 系统 MUST 在每个阶段边界记录以下信息：阶段名称、开始时间、结束时间、输入记录数、输出记录数、校验通过数、校验失败数、执行状态
- **FR-019**: 异常发生时，系统 MUST 记录异常类型、异常消息、堆栈跟踪、触发异常的上下文数据
- **FR-020**: 系统 MUST 支持按日期、管道运行 ID、阶段名称检索日志记录
- **FR-021**: 系统 MUST 在管道运行结束时输出概要日志，汇总整条管道的执行状态和数据流转统计

### Key Entities

- **管道运行记录 (Pipeline Run)**: 代表一次完整的管道执行实例，包含运行 ID、执行日期、目标数据日期、开始/结束时间、整体状态（运行中/成功/部分失败/熔断/已中断）、各阶段耗时统计
- **阶段执行记录 (Stage Execution)**: 代表管道中单个阶段的执行实例，包含阶段名称、所属管道运行 ID、执行顺序、开始/结束时间、输入记录数、输出记录数、校验通过数、校验失败数、执行状态（等待中/运行中/成功/失败/熔断/超时）、异常严重等级（Info/Error/Critical）
- **校验违规记录 (Validation Violation)**: 代表单条数据校验失败的具体信息，包含所属阶段、记录标识、违规字段、期望约束、实际值、违规时间
- **熔断状态 (Circuit Breaker State)**: 代表管道或阶段的熔断状态，包含状态值（闭合/半开/断开）、触发原因、触发时间、连续失败计数、最近失败详情
- **管道模式定义 (Pipeline Schema)**: 代表某个管道阶段输入/输出的数据模式，包含字段名、数据类型、是否必填、值域约束（最小值/最大值/枚举值）、默认值；输出模式与下游阶段的输入模式形成显式契约关系，上游变更时自动校验下游兼容性

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 所有管道阶段的输入/输出校验在 1 秒内完成（百条记录以下量级），不影响管道正常吞吐
- **SC-002**: 代码变更后运行管道完整性测试套件，从提交测试到获得完整报告的时间不超过 5 分钟
- **SC-003**: 单次管道运行中，至少 90% 的数据格式异常记录（字段缺失、类型错误、值域违规）在阶段输出校验点被拦截，不流入下游持久化存储
- **SC-004**: 熔断触发后，下游阶段在 1 秒内停止执行，错误数据零扩散至下游持久化存储
- **SC-005**: 运维人员通过日志在 3 分钟内定位到异常发生的具体阶段和违规记录
- **SC-006**: 管道完整性测试套件覆盖 100% 的核心数据流转路径（采集→摄入→处理→分析）
- **SC-007**: 管道护栏机制引入后，因代码变更导致的数据管道故障减少 80%
- **SC-008**: 所有管道阶段在正常数据流下，护栏校验与日志记录的总耗时不超过管道纯业务逻辑执行时间的 5%（以未启用护栏时的执行耗时为基准）

## Assumptions

- 管道护栏机制作为 DataPipeline 模块的内建功能实现，不引入新的外部服务依赖
- 护栏采用独立编排层模式（GuardPipeline）包装现有 FinancialPipeline，PipelineContext 和所有 Stage 类保持零改动
- 数据模式定义沿袭 DataPipeline 当前已有的配置管理模式（`DataPipeline/config.py` Config 类），新增配置项遵循配置即契约原则
- 熔断状态按管道运行实例隔离（每个运行 ID 有独立的熔断状态），不同日期或批次的管道运行互不影响
- 告警通知初期以结构化日志形式输出（FR-009 的基本要求），外部通知渠道（邮件、消息推送）作为后续迭代
- 校验规则的声明式定义使用 Python 原生方案（如 Pydantic 模型或自定义装饰器），不引入新的第三方校验框架
- 测试用例使用项目已有的测试框架（Pytest），Fixture 数据基于历史真实数据的脱敏样本
- 日志存储采用追加写入方式，由运维定期清理或归档，本功能不强制实现自动归档
- 管道中间阶段熔断中断时，已写入下游的数据不回滚（管道当前设计为日级批处理，通过幂等重跑修复）
- 管道 10 个阶段（S1-S10）均需要护栏覆盖，但分阶段交付：P1（S1-S7 核心处理阶段）优先，P2（S8-S10 分析阶段）次之
- 基线快照使用历史真实数据的脱敏固定样本生成，样本数据一经确定不随日常管道运行变化，仅在 Code Review 确认后手动更新

- 依赖项目已有的 Pytest 测试基础设施
- 依赖项目 CI 流水线（代码提交/PR 触发自动化检查）
