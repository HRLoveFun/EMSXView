## 2. 目标拆解机制

### 2.1 拆解原则

将宏大计划分解为 Agent 可独立执行的子任务, 遵循 **SMART** 原则:

| 原则 | 说明 | 反例 | 正例 |
|------|------|------|------|
| **S**pecific | 目标明确, 无歧义 | "优化存储性能" | "将 raw_bdib.db 从 68GB 裁剪到 ≤23GB" |
| **M**easurable | 可量化, 有验收标准 | "提升查询速度" | "单 ticker 单日查询 ≤200ms" |
| **A**chievable | Agent 可独立完成 | "重构整个系统" | "将 init_raw_bdib_schema 提取到 inline_ddl.py" |
| **R**elevant | 与上层目标对齐 | "优化前端颜色" (与存储分层无关) | "实现 UnifiedReader Hot 路由" |
| **T**ime-bound | 有时间约束 | "尽快完成" | "Phase 0: 3 天内完成" |

### 2.2 拆解层次模型

```
Level 0: 宏大计划 (Grand Plan)
    ├── 目标: 将 88GB 数据优化迁移至 Hot (≤25GB) + Cold 分层架构
    ├── 工期: 15 天
    ├── 约束: 查询性能提升 3-10x, 零停机迁移
    └── 验收: 5 年存储从 >800GB 降至 ~293GB
         │
         ▼
Level 1: 里程碑 (Milestones) — 每个里程碑有明确的质量门禁
    ├── M0: 基础设施就绪 (Day 3)
    │   └── Gate: 单月 Parquet 归档可演练
    ├── M1: 核心引擎完成 (Day 8)
    │   └── Gate: UnifiedReader Hot+Cold 路由全部测试通过
    ├── M2: 全量迁移完成 (Day 11)
    │   └── Gate: 88GB → Hot+Cold, 回归测试全通过
    └── M3: 生产上线 (Day 15)
        └── Gate: Cron 自动化, CLI 完整, 文档齐备
             │
             ▼
Level 2: 迭代 (Iterations) — 每个迭代有明确的交付物
    ├── I0.1: 存储层包结构 + tiering_config.py          (Day 1-2)
    ├── I0.2: 依赖安装 + 测试夹具                         (Day 2-3)
    ├── I1.1: parquet_archive.py                         (Day 4-5)
    ├── I1.2: unified_reader.py                          (Day 5-6)
    ├── I1.3: archive_manager.py                         (Day 6-7)
    ├── I1.4: archive_audit.py                           (Day 7-8)
    ├── I2.1: 单月演练 (2026-01)                         (Day 9-10)
    ├── I2.2: 全量迁移                                   (Day 10-11)
    └── I2.3: 回归测试 + 基准测试                         (Day 11)
             │
             ▼
Level 3: 子任务 (Tasks) — Agent 的最小可执行单元
    ├── T1: 创建 CostView/src/storage/__init__.py
    ├── T2: 实现 TieringConfig 数据类 + JSON 持久化
    ├── T3: 实现 TieringConfig.load/save 方法
    ├── T4: 编写 test_tiering_config.py
    ├── T5: 注册到 __main__.py CLI
    └── ...
```

### 2.4 拆解检查清单

在将计划交付给 Agent 执行前, 需逐项确认:

```
□ 1. 每个 Level 3 子任务是否满足 SMART 原则？
□ 2. 子任务的前置依赖是否已明确标注？
□ 3. 验收标准是否可自动化验证 (脚本/命令)？
□ 4. 每个子任务是否有明确的回滚条件？
□ 5. 子任务之间的边界是否清晰 (无重叠责任)？
□ 6. 是否存在 "20% 未知因素需探索" 的子任务标记？
□ 7. 所有文件路径是否准确 (绝对路径或可解析的相对路径)？
□ 8. 是否需要引入新的依赖？是否评估了兼容性？
```

## 3. 质量控制流程

### 3.1 三层质量门禁体系

```
第一层: 即时门禁 (Instant Gate)
├── 触发: 每次代码编辑完成后
├── 执行: Agent 自动运行
├── 检查项:
│   ├── 编译检查 (python -m compileall)
│   ├── 语法错误 (SyntaxError, ImportError)
│   └── 被修改文件的单元测试
└── 违规处理: 阻塞当前子任务, 修复后才能继续

第二层: 增量门禁 (Incremental Gate)
├── 触发: 每个子任务完成时
├── 执行: Agent 自动 + Human 可选确认
├── 检查项:
│   ├── 全模块单元测试 (pytest module/)
│   ├── Lint 检查 (flake8/pyright)
│   ├── 覆盖率增量 (--cov-report=)
│   └── 架构合规检查 (循环依赖检测)
└── 违规处理: 阻塞当前迭代, 插入修复子任务

第三层: 里程碑门禁 (Milestone Gate)
├── 触发: 每个里程碑完成时
├── 执行: Human + Agent 联合评审
├── 检查项:
│   ├── 全量回归测试 (pytest)
│   ├── 性能基准测试 (比较改进前后数据)
│   ├── 文档完整性检查
│   ├── 风险状态回顾
│   └── 与上层目标一致性校验
└── 违规处理: 暂停计划, 需 Human 决策是否继续/回滚/调整
```

### 3.2 门禁自动化链 (参考 autopilot-policy.yaml)

```yaml
# 每次 Issue 实施后的自动化验证链
verification_chain:
  description: "每个子任务完成后自动执行的验证步骤"
  steps:
    - id: compile-check
      command: "python -m compileall CostView/src DataPipeline/src -q"
      error_code: "E_VERIFY_BUILD_FAILED"
      retryable: false            # 编译失败不可重试, 必须修复
      auto_approve: true          # 自动执行, 无需人工确认

    - id: unit-tests
      command: >
        python -m pytest CostView/tests/ DataPipeline/tests/
        -x --timeout=60 -q
        --tb=short
      error_code: "E_VERIFY_TEST_FAILED"
      retryable: true             # 瞬态失败可重试
      max_retries: 2
      auto_approve: true

    - id: integration-tests
      command: >
        python -m pytest tests/test_pipeline_guards.py
        tests/test_unified_reader.py
        -x --timeout=120 -q
      error_code: "E_VERIFY_INTEGRATION_FAILED"
      retryable: false

    - id: lint-check
      command: >
        flake8 CostView/src/storage/ --max-line-length=100
        --statistics --exit-zero
      error_code: "E_VERIFY_LINT_FAILED"
      retryable: false

    - id: sync-status
      command: >
        python scripts/workflow/sync_execution_status.py

      retryable: true
      max_retries: 3
      auto_approve: true
```

### 3.3 门禁违规处理流程

```
门禁违规触发
    │
    ├──→ 自动修复 (Auto-fix)
    │     适用: 常见 lint 错误、格式问题、import 排序
    │     处理: Agent 自动修正后重新运行门禁
    │     记录: iteration-log 添加 fix 记录
    │
    ├──→ 回滚重试 (Rollback & Retry)
    │     适用: 编译错误、测试失败、逻辑错误
    │     处理: 回退到上一个通过门禁的状态, 重新执行子任务
    │     记录: iteration-log 记录失败原因 + 修复方法
    │
    ├──→ 插入修复任务 (Insert Fix Task)
    │     适用: 设计缺陷、架构违规、性能退化
    │     处理: 在当前迭代中插入修复子任务, 完成后重新验证
    │     记录: iteration-log + risk-register 更新
    │
    └──→ 升级至 Human (Escalate)
        适用: 技术路线争议、重大设计变更、资源不足
        处理: 暂停计划, 生成决策简报 → Human 决策
        记录: 完整的选项分析 + 推荐方案
```

## 5. 动态调整策略

### 5.1 调整触发条件

| 触发条件 | 示例 | 调整类型 | 决策权 |
|---------|------|---------|--------|
| 子任务预估偏差 >150% | unified_reader 原估 3h, 实际 6h | 拆分任务/延长工期 | Agent |
| 连续 3 次门禁失败 | archive_manager 测试连环失败 | 技术方案调整 | Agent → Human |
| 发现未预见的依赖 | Parquet 需要新版本 PyArrow 不兼容 | 插入适配任务 | Agent |
| 需求变更 | 用户要求 Hot 窗口改为 60 天 | 参数调整 | Human |
| 技术路线不可行 | 谓词下推在 PyArrow 某版本有 bug | 方案替代 | Agent → Human |
| 资源受限 | 磁盘空间不足, 无法同时保留 Hot+Cold | 阶段调整 | Human |

### 5.2 四类调整策略

```
Strategy A: 参数调整 (Parameter Tuning)
    适用: 配置类参数需修改
    操作: 修改 tiering_config.json, 无需代码变更
    风险: 低
    示例: Hot 窗口 50天 → 45天

Strategy B: 任务重组 (Task Recomposition)
    适用: 子任务粒度过大或过小
    操作: 拆分为更小子任务 / 合并相关子任务
    风险: 低
    示例: "实现 archive_manager" → "实现 archive_month" + "实现 trim_hot_tier"

Strategy C: 方案替代 (Solution Substitution)
    适用: 原定技术方案不可行
    操作: 保留目标, 更换实现路径
    风险: 中
    示例: PyArrow read_table 性能不达标 → 改用 DuckDB 读取 Parquet

Strategy D: 范围调整 (Scope Adjustment)
    适用: 宏大计划的目标需要修正
    操作: 调整交付范围或时间线
    风险: 高 (需 Human 批准)
    示例: "全量迁移" → 先迁移 raw_bdib, 其他表延后
```

### 6.3 串行 vs 并行执行策略

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 串行执行 (默认路径)                                                       │
│                                                                         │
│  T1 → T2 → T3 → T4 → GATE → T5 → T6 → T7 → GATE                       │
│                                                                         │
│ 适用: 有强依赖链的任务                                                    │
│ 示例: unified_reader 必须先于 archive_manager 实现                       │
│ 优点: 清晰的依赖关系, 简单可预测                                           │
│ 缺点: 总工期 = 各任务时间和                                                │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ 并行执行 (加速路径)                                                       │
│                                                                         │
│  T1 ──┐                                                                 │
│  T2 ──┤──→ GATE → T5 → ...                                              │
│  T3 ──┘                                                                 │
│                                                                         │
│ 适用: 无交叉依赖的独立任务                                                 │
│ 示例: parquet_archive.py 和 archive_audit.py 可并行开发                   │
│ 优点: 总工期 = 最长路径, 加速 2-3x                                        │
│ 缺点: 需要更仔细的冲突管理, 测试更复杂                                      │
│ Agent 策略: 使用 ThreadPoolExecutor 语义, 每个独立路径一个 Coding Agent   │
└─────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────┐
│ 管道执行 (最优路径)                                                       │
│                                                                         │
│  T1 → T2 → T3 ──┐                                                       │
│                  ├──→ GATE → T7 → T8                                     │
│  T4 → T5 → T6 ──┘                                                       │
│                                                                         │
│ 适用: 混合依赖的大计划                                                     │
│ 示例: Phase 1 中 parquet_archive(T1-T3) 和 unified_reader(T4-T6) 并行    │
```

### 12.2 回顾检查清单

每次里程碑完成后, 执行以下回顾:

```
□ 1. 预估 vs 实际偏差分析: 哪些任务估时不准? 下次如何改进?
□ 2. 门禁失败根因: 最常见的失败原因? 是否可前置发现?
□ 3. 调整记录回顾: 哪些调整本可以避免? 哪些调整值得标准化?
□ 4. Agent 协作效率: 并行任务是否有冲突? Handoff 是否顺畅?
□ 5. 知识沉淀: 哪些经验可写入 memory/repo? 哪些错误模式可记录?
□ 6. 模板改进: 现有模板是否需要补充或优化?
□ 7. Human 体验: Human 介入的频率和时间是否符合预期?
```

### B. 常见陷阱与对策

| 陷阱 | 表现 | 对策 |
|------|------|------|
| 拆解过细 | 子任务太多, 管理开销 > 执行收益 | 子任务粒度: 1-3 小时可完成; 不超过 50 个/Phase |
| 门禁过严 | 每次小改动都要跑全量测试 | 分三层门禁: 即时/增量/里程碑, 只有里程碑跑全量 |
| 过度并行 | 并行任务间协调成本 > 加速收益 | 仅对无依赖的任务并行; 最多 3 路并行 |
| 计划迷信 | 拒绝调整, 坚持已有计划 | 每次门禁失败都问 "计划是否需要调整?" |
| 文档滞后 | 状态文档落后于实际进展 | 每次同步更新, 不超过 1 次会话的延迟 |
| Human 疲劳 | Human 被过多升级请求淹没 | 绿色自动, 黄色通知, 红色才升级 |
