# Agent 执行实战手册 — 工具映射与门禁实现

> **日期**: 2026-05-08 | **版本**: v1.0
> **目的**: 将 `agent-execution-framework.md` 的理论框架映射为可执行的 Agent 工具调用和门禁命令
> **速查**: 不知道当前该做什么 → 看 §流程图 | 不知道门禁怎么跑 → 看 §门禁命令表

---

## 1. 一句话执行原则

```
每次只做一个子任务 → 改完就跑门禁 → 绿灯继续 / 红灯修复 / 黄灯问 Human
```

## 2. 工具→框架映射总表

这是整个框架落地最关键的对照表。每个框架概念直接映射到 VS Code 中的一个具体工具调用。

```mermaid
┌─────────────────────────┬──────────────────────────────────┬──────────────────────┐
│   框架概念              │   具体工具调用                    │   执行人              │
├─────────────────────────┼──────────────────────────────────┼──────────────────────┤
│ 拆解宏大计划             │ runSubagent(task-planner,        │ Task Planner Agent   │
│                         │   "拆解 {计划名} 为子任务")       │                      │
│ 迭代进度追踪             │ manage_todo_list(更新状态)        │ Coding Agent (每个    │
│                         │                                  │ 子任务完成后)         │
│ 偏差检测                 │ get_terminal_output +            │ Coding Agent (每次    │
│                         │ 比较实际耗时 vs todo 预估         │ 子任务开始时记时)      │
│ 即时门禁(编译)           │ get_errors(被修改的文件)          │ Coding Agent (每次    │
│                         │                                  │ 文件保存后)           │
│ 即时门禁(测试)           │ run_in_terminal(                 │ Coding Agent (每次    │
│                         │  "pytest 相关测试 -x")            │ 改完一批代码后)       │
│ 增量门禁(全模块测试)     │ run_in_terminal(                 │ Coding Agent (每个    │
│                         │  "pytest {module}/tests/ -x")     │ 子任务完成时)         │
│ 知识库查错               │ mcp_emsx-knowledg_               │ error-resolver Agent  │
│                         │  search_error_patterns(查询)      │ (门禁失败时自动调用)   │
│ 记录错误模式             │ mcp_emsx-knowledg_               │ Coding Agent (新错误  │
│                         │  add_error_pattern(...)           │ 修复后记录)           │
│ 持久化迭代记录           │ mcp_emsx-knowledg_               │ Coding Agent (每次    │
│                         │  add_iteration_entry(...)         │ 会话结束或里程碑完成)  │
│ Human 进度同步           │ manage_todo_list(看板) +         │ Coding Agent → Human │
│                         │ 文本消息 + vscode_askQuestions    │                      │
│ Human 异常升级           │ vscode_askQuestions(              │ Coding Agent → Human │
│                         │  选项: [方案A, 方案B, 自定义])     │ (红色信号触发)        │
│ 里程碑评审               │ run_in_terminal(全量命令) +       │ Coding Agent + Human │
│                         │ 文本消息 + vscode_askQuestions    │                      │
│ 前置调研                 │ runSubagent(Explore, "调研...")   │ Explore Agent         │
│                         │ → 读取返回的结构化报告             │ (每个迭代开始前)       │
│ 风险状态检查             │ mcp_emsx-knowledg_               │ Coding Agent (每次    │
│                         │  get_iteration_log() → 分析风险   │ 门禁后自动检查)        │
└─────────────────────────┴──────────────────────────────────┴──────────────────────┘
```

## 3. 单次子任务执行流程图 (Agent 实际执行步骤)

这是 Agent 执行 **一个子任务** 时的完整步骤序列。每个框 = 一次工具调用。

```
┌──────────────────────────────────────────────────────────────────────────┐
│  START: 接到子任务 T{n}: "{任务名}"                                      │
│  预估: {X}h | 前置: {T-m} | 文件: {file_a.py, file_b.py}               │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 0: 前置调研 (如需要)                                                │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │ runSubagent(Explore, "调研 {module} 的现有代码结构和接口")           │  │
│  │ → 等待返回结构化报告                                               │  │
│  │ → 若报告不完整, 追问具体问题                                        │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: ~2-5 分钟                                                         │
│  注意: 如果子任务是对已有代码的小修改, 跳过此步                            │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 1: 读取需要修改的文件 + 理解上下文                                   │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │ read_file(file_a.py, 1-200) → 理解现有逻辑                         │  │
│  │ read_file(file_b.py, 1-150) → 理解上下游接口                       │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: ~1-3 分钟                                                         │
│  注意: 读够上下文再改, 不要边猜边改                                      │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 2: 编写代码 (循环: 改一点 → 检查一点)                                │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │ 2a. replace_string_in_file / create_file (编辑/新建文件)           │  │
│  │ 2b. get_errors(已修改文件) → 如报错, 修复 → 重复 2a              │  │
│  │ 2c. 如有新测试: create_file(test_xxx.py, ...)                      │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: 预估时间的 60%                                                    │
│  注意: 每改 3-5 个逻辑点就 run_in_terminal 跑一次相关测试, 不要攒到最后    │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 3: 即时门禁 — 编译检查                                               │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │ run_in_terminal("python -m compileall {改过的文件} -q")            │  │
│  │                                                                   │  │
│  │ 结果:                                                             │  │
│  │  ✅ 通过 → 继续                                                   │  │
│  │  ❌ 失败 → 修复语法错误 → 回到 Step 2                              │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: ~10 秒                                                           │
│  自动/人工: 完全自动 — Agent 无需问 Human                                │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 4: 即时门禁 — 单元测试                                               │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │ run_in_terminal(                                                   │  │
│  │   "pytest {测试文件路径} -x --tb=short --timeout=60 -q"            │  │
│  │ )                                                                  │  │
│  │                                                                   │  │
│  │ 结果:                                                             │  │
│  │  ✅ 全部通过 → 继续                                               │  │
│  │  ❌ 失败 →  分析失败原因 → 回到 Step 2                              │  │
│  │        │      如果是已知错误模式 → mcp_emsx-knowledg_              │  │
│  │        │        search_error_patterns → 按已知方案修复              │  │
│  │        │      如果是新错误  → 正常修复                             │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: ~30 秒 - 5 分钟 (取决于测试复杂度)                                 │
│  自动/人工: 完全自动 — Agent 自行分析失败原因并修复                        │
│  注意: 如果连续 2 次修复失败 → 进入异常升级 (Step 7)                      │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 5: 更新 todo + 记录日志 (子任务完成)                                 │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  │ manage_todo_list(更新 T{n} 为 completed)                           │  │
│  │                                                                   │  │
│  │ 实际耗时: {X}h (对比预估)                                          │  │
│  │ • 如果 > 预估 1.5x → 记录偏差原因 → 用于后续估时校准                │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: ~30 秒                                                           │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 6: 增量门禁 — 全模块测试 + 架构检查                                  │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  6a. run_in_terminal(                                                │  │
│       "pytest {模块}/tests/ -x --tb=short --timeout=120 -q")          │  │
│  6b. get_errors({模块}/src/) → 检查编译+lint                          │  │
│  6c. 检查范围蔓延: 改的文件数是否 ≤ 计划数 × 2                        │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│                                                                         │
│  结果:                                                                   │
│  ✅ 全部通过 → 继续下一个子任务                                          │
│  ❌ 失败 →                                                              │
│       • 如果是测试失败 → 分析是 "新代码 bug" 还是 "旧代码暴露"            │
│       • 如果是新代码 bug → 修复, 回到 Step 2                            │
│       • 如果是旧代码暴露 → 记录该问题, 继续 (不阻塞当前子任务)             │
│  🟡 范围蔓延 > 2x → vscode_askQuestions(                               │
│       "改的文件数超出计划 {N}x, 是否提取为独立子任务?")                   │
│                                                                         │
│  注意: 此门禁是 Agent 自动执行和判断的, 只有黄色信号才需问 Human          │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   ▼
┌──────────────────────────────────────────────────────────────────────────┐
│  Step 7: 异常升级 (仅在需要时)                                            │
│  ┌────────────────────────────────────────────────────────────────────┐  │
│  IF (连续 2 次修复失败)                                               │  │
│   OR (发现设计方案不可行)                                             │  │
│   OR (需要 Human 提供 Bloomber 凭证/配置/决策)                        │  │
│  THEN:                                                               │  │
│    vscode_askQuestions([                                             │  │
│      "问题: {一句话描述}",                                           │  │
│      "已尝试: {3 种方案及结果}",                                      │  │
│      "推荐: {方案 A}",                                               │  │
│      "选项: [方案A, 方案B, 我来给新方案]"                             │  │
│    ])                                                                │  │
│  └────────────────────────────────────────────────────────────────────┘  │
│  耗时: ~5 分钟 (等待 Human 回复)                                        │
│  注意: 只有在红色信号时才升级, 不要每遇到小问题就问 Human                 │
└──────────────────────────────────────────────────────────────────────────┘

                 ──── 子任务 T{n} 完成, 开始 T{n+1} ────
```

## 4. 质量门禁实现详解 (代码级)

### 4.1 即时门禁 (Instant Gate) — 每次代码编辑后

```
┌──────────────────────────────────────────────────────────────────────────┐
│  触发: Agent 执行完一次 replace_string_in_file 或 create_file 后          │
│  目标: 确保当前修改没有引入基本错误                                        │
│  耗时: <30 秒                                                           │
│  自动化程度: 100% 自动                                                  │
│  Human 介入: 无需                                                       │
├──────────────────────────────────────────────────────────────────────────┤
│  执行步骤:                                                               │
│                                                                         │
│  Step 1: 编译检查                                                       │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 工具: get_errors(被修改文件的路径)                                 │   │
│  │ 命令: 无需额外命令, VS Code 语言服务已经实时检测                    │   │
│  │ 判断: errors 列表为空 → ✅                                        │   │
│  │       errors 非空 → ❌ 逐个修复                                    │   │
│  │ 示例输出:                                                         │   │
│  │   [{                                                              │   │
│  │     "message": "import 'pd' could not be resolved",               │   │
│  │     "file": "CostView/src/storage/unified_reader.py",             │   │
│  │     "line": 5                                                     │   │
│  │   }]                                                              │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 2: 无参数错误 (Python 特有)                                        │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 工具: run_in_terminal                                            │   │
│  │ 命令: python -m compileall {修改的文件路径} -q                    │   │
│  │ 说明: 捕获 get_errors 可能遗漏的运行时 SyntaxError               │   │
│  │ 示例:                                                            │   │
│  │   cmd> python -m compileall CostView/src/storage/unified_reader.py│   │
│  │   ✅ 无输出 = 通过                                               │   │
│  │   ❌ SyntaxError: invalid syntax → 行号+错误 → 修复              │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 3: 可选 — 新代码的快速冒烟测试 (如果测试文件存在)                  │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 工具: run_in_terminal                                            │   │
│  │ 命令: pytest {被修改文件的测试路径} -x --no-header -q            │   │
│  │ 注意: 不是全量测试, 只跑被修改文件对应的测试                        │   │
│  └──────────────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────┘
```

### 4.2 增量门禁 (Incremental Gate) — 每个子任务完成后

```
┌──────────────────────────────────────────────────────────────────────────┐
│  触发: 子任务 T{n} 的所有代码修改完成 + 即时门禁通过                       │
│  目标: 确保该子任务的整体交付质量, 不污染模块                             │
│  耗时: 1-5 分钟                                                         │
│  自动化程度: 95% 自动 (范围检查为黄色时问 Human)                         │
│  Human 介入: 仅当范围蔓延 >2x 或测试暴露了旧代码问题                      │
├──────────────────────────────────────────────────────────────────────────┤
│  执行步骤:                                                               │
│                                                                         │
│  Step 1: 全模块测试                                                      │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 工具: run_in_terminal                                            │   │
│  │ 命令:                                                             │   │
│  │   pytest {affected_module}/tests/ \                              │   │
│  │     -x --tb=short --timeout=120 -q                               │   │
│  │                                                                  │   │
│  │ 示例 (存储分层 Phase 0 完成后):                                   │   │
│  │   cmd> pytest CostView/tests/ \                                  │   │
│  │         tests/test_tiering_config.py -x --tb=short -q            │   │
│  │   ✅ 6 passed in 2.34s                                           │   │
│  │                                                                  │   │
│  │ 失败分析:                                                         │   │
│  │  ❌ FAILED test_tiering_config.py::test_save_load -               │   │
│  │      AssertionError: assert {'hot_window': 50} == {...}          │   │
│  │  → 分析: test_save_load 期望的 key 名与实现不匹配                   │   │
│  │  → 修复: 统一 key 命名 (camelCase vs snake_case)                 │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 2: 架构合规性检查                                                  │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 工具: run_in_terminal                                            │   │
│  │ 命令:                                                            │   │
│  │   # 检查循环依赖                                                  │   │
│  │   python -c "                                                    │   │
│  │   import sys; sys.tracebacklimit=0                                │   │
│  │   from CostView.src.storage import unified_reader               │   │
│  │   print('import OK')                                             │   │
│  │   "                                                              │   │
│  │                                                                  │   │
│  │   # 检查文件行数 (架构指令: ≤500 行)                              │   │
│  │   python -c "                                                    │   │
│  │   for f in ['unified_reader.py', 'archive_manager.py']:          │   │
│  │       lines = open(f'CostView/src/storage/{f}').count('\\n')     │   │
│  │       assert lines <= 500, f'{f}: {lines} > 500'                │   │
│  │       print(f'{f}: {lines} lines OK')                            │   │
│  │   "                                                              │   │
│  │                                                                  │   │
│  │ 通过条件: import OK + 每个文件 ≤500 行                             │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 3: 范围蔓延检查                                                    │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 方法: get_changed_files() 列出当前修改的文件                       │   │
│  │ 对比: 计划中声明的文件列表                                         │   │
│  │                                                                  │   │
│  │ 逻辑:                                                             │   │
│  │  实际改的文件数 ≤ 计划文件数 × 2 → ✅ 继续                        │   │
│  │  实际改的文件数 > 计划文件数 × 2 → 🟡 问 Human:                   │   │
│  │    "修改了 {N} 个文件 (计划 {M}), 是否:                           │   │
│  │     [A] 接受范围蔓延, 继续                                       │   │
│  │     [B] 拆分出额外文件为独立子任务                                │   │
│  │     [C] 回滚额外修改"                                            │   │
│  └──────────────────────────────────────────────────────────────────┘   │
│                                                                         │
│  Step 4: 日志记录                                                       │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 工具: mcp_emsx-knowledg_add_iteration_entry                     │   │
│  │ 写入:                                                            │   │
│  │   entry_type: task                                               │   │
│  │   trigger: "T{n}: {任务名} 完成"                                 │   │
│  │   action: "修改 {文件列表}; 门禁: {通过/失败/修复}"               │   │
│  │   outcome: "{测试结果}, 耗时 {实际}h (预估 {预估}h)"             │   │
│  └──────────────────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────────────────┘
```

### 4.3 里程碑门禁 (Milestone Gate) — 每个阶段完成后

```
┌──────────────────────────────────────────────────────────────────────────┐
│  触发: 该里程碑下的所有子任务全部完成 + 增量门禁全部通过                    │
│  目标: 确保该阶段整体质量, 做 Human 可见的正式验收                         │
│  耗时: 10-30 分钟                                                       │
│  自动化程度: 70% 自动执行检查 + 30% Human 评审判断                       │
│  Human 介入: 必须 — 里程碑门禁需要 Human 最终批准                         │
├──────────────────────────────────────────────────────────────────────────┤
│  执行步骤:                                                               │
│                                                                         │
│  Step 1: Agent 自动运行全量检查 (生成报告)                                │
│  ┌──────────────────────────────────────────────────────────────────┐   │
│  │ 以下检查由 Agent 自动执行, 结果汇总到里程碑报告:                    │   │
│  │                                                                  │   │
│  │  # 1a. 全量回归测试                                               │   │
│  │  run_in_terminal(                                                │   │
│  │   "python -m pytest CostView/tests/ DataPipeline/tests/ \        │   │
```

## 8. 常见场景处理速查

### 场景 1: 编译通过了但测试失败

```
问题: pytest 报错, 但不是语法错误
处理:
1. 读取测试失败输出 → 找到 assert 失败的行和期望值
2. 分析是新代码逻辑错还是测试用例需要更新
3. 修复 → 重新 run_in_terminal(pytest -x)
4. 如果连续 2 次修复不通过 → vscode_askQuestions 升级
不问 Human: 小 assert 错、字段名不匹配、import 漏了
要问 Human: 业务逻辑理解有歧义、测试框架问题、依赖版本冲突
```

### 场景 2: 发现需要改的文件比计划多

```
问题: 改到一半发现还有 3 个文件需要修改
处理:
1. 记下额外文件列表和原因
2. 继续完成当前子任务 (不中途切换)
3. 增量门禁时 → 范围检查会触发 🟡
4. vscode_askQuestions("额外修改了 {N} 个文件: {列表}。是否:
   A. 纳入当前子任务
   B. 拆分为新子任务 T{n+1}")
不问 Human: 多 1-2 个小文件且修改简单
要问 Human: 多 3+ 文件或涉及架构变动
```

### 场景 3: 子任务做到一半发现方案不 work

```
问题: 实现到一半发现原定技术方案行不通
     (例如: PyArrow read_table 在 Windows 上路径处理有 bug)
处理:
1. STOP — 立即停止当前实现
2. 花 5 分钟探索替代方案: runSubagent(Explore, "调研 PyArrow Windows 路径方案")
3. 生成替代方案分析 (至少 2 个选项)
4. vscode_askQuestions → Human 决策
不问 Human: 小参数调整 (compression level、row group size)
要问 Human: 库替代 (PyArrow→DuckDB)、架构调整、新增依赖
```

### 场景 4: Human 中途给了新需求

```
问题: 正在做 T4, Human 说 "顺便把 X 也做了"
处理:
1. manage_todo_list(插入新子任务到迭代末尾)
2. 继续当前 T4 (不中断)
3. T4 完成后, 依次执行新插入的任务
不问 Human: 不需要 — 直接加入 todo list
注意: 如果新需求会影响当前 T4 的接口 → 暂停 T4, 先规划新需求的依赖
```

## 附录: 执行速查卡片

```markdown
# 执行速查卡片 (打印版)

## 每次子任务的步骤
□ Step 0: Explore 前置调研 (如需要)
□ Step 1: read_file 读上下文
□ Step 2: 写代码 → get_errors → 循环
□ Step 3: 即时门禁: compileall + pytest 相关测试
□ Step 4: 更新 todo (completed + 实际耗时)
□ Step 5: 增量门禁: 全模块测试 + 架构检查 + 范围检查
□ Step 6: 记录 iteration_log

## 颜色决策
🟢 不问: 编译错/测试失败/lint警告/import问题
🟡 可选问: 时间偏差>150% / 范围>2x / 性能退化<20%
🔴 必须问: 连续3次失败 / 方案不work / 架构决策 / 数据风险

## 常用门禁命令
编译:    python -m compileall {path} -q
测试:    pytest {path} -x --tb=short -q
全量:    python -m pytest {模块}/tests/ -x --timeout=300 -v
架构:    python -c "from {模块} import {类}; print('OK')"
```

> **总结**: 这套体系的核心不在于文档有多厚, 而在于 **每个门禁都有对应的可执行命令**、**每个颜色都有明确的判断标准**、**每种异常都有预设的处理路径**。Agent 照着这个 playbook 执行, 80% 的决策完全自动, 15% 自动执行+通知 Human, 只有 5% 需要 Human 深度介入。
