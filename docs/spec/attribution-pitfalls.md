## 使用方式：两类条目，用途不同

本清单的条目分两类，**不要混用**：

| 类型 | 作用 | 判定时机 | 本清单中的分布 |
|---|---|---|---|
| **规则 / 原则** | 决定**事后**能不能说清（复盘有语言） | 事后 | 多数条目 |
| **检查项** | 决定**当场**能不能拦住（一句话可判） | 当场 | 见下「当场问法汇表」 |

**关键区别**（由 T20~T23 协作中的实际观察得出）：

> 规则的作用是**让复盘有语言，不是让错误在当场被拦住**。

一条原则写得再准（如「不可逆约束必须实测」），当场也不会自动生效 —— 因为**它要求的是「意识到」，
而意识无法自省**。所以每条规则都应配一句**当场可判**的问法，判据是
**「能不能当场贴出东西」**，而不是「我有没有意识到」：

| 编号 | 当场问法（可判、可交接） |
|---|---|
| AT-01 | 这个顺序是**声明**的还是**观测**的？ |
| AT-02 | 我引用的「相邻」来自**哪一层**？与被解释对象同层吗？ |
| AT-03 | 我的解释能**完整**复现观测吗？ |
| AT-04 | **机制失效时，我这次的输入还能通过吗？** |
| AT-05 | 这条结论我是**读代码 / 实测**得到的，还是**转述**的？ |
| AT-06 | 我是否**省略**了「曾怀疑 X、后来自纠」这段？ |
| AT-07 | 给出结论前：我刚才**改过运行条件**吗？改回去还能复现吗？ |
| AT-08 | 我的结论是「**修复有效**」还是「**这就是根因**」？ |
| AT-09 | 这个边界值，我**贴得出实测依据**吗？（贴不出 → 去测，通常几秒） |
| AT-10 | 这个值**自称**保守 / 安全吗？—— **自称不是证据** |
| AT-11 | 这个边界结论，我**贴得出聚合数据**吗？我的**结构推理**推广到了哪些实例、**逐一核对过**吗？ |
| AT-12 | 我选的这个验证方式**有可能失败**吗？我是不是因为**它不会失败**才选的？ |
| AT-13 | 我完成的是**第几步**？**下一步谁负责**（能一句话答出名字或工具吗）？ |
| AT-14 | 我推断用的指标，与目标指标的**计算依赖**相同吗？（逐行 / 逐组 / 全局） |

**用法**：不必背规则；**在给出结论前挑一条念出来，并尝试贴出证据**。贴不出 → 说明该补证据。

## 为什么需要这个清单

T20 的归因过程是这样的：本侧在 `fill_bdib` 里发现 `log_chg_pct_10s` 出现 −9.7 / +7.4
量级的值（10 秒对数收益物理上不可能），然后尝试**从数据反推原因**。这个反向归因过程中
连续踩了三个陷阱：

1. 把「观测到的行序」当作数据的稳定属性，并据此推理（AT-01）；
2. 用**存储层**的相邻关系去解释**计算层**的配对（AT-02）；
3. 有一个明确的反常信号（重算对不上），用一个"次因"解释后就继续，还把它称作「铁证」（AT-03）。

三者叠加，使一个**结论正确但推理不成立**的判断进入了文档。更值得警惕的是：
**如果当时观测顺序稍有不同，同样的推理会得出错误结论** —— 这正是清单要防的。

---

## AT-01 禁把「观测顺序」当「契约」

**严重度**: high
**描述**: 把一次观测到的数据排列（行序 / SQL 返回序 / 分组序 / 文件序）当作数据的
**稳定属性**，并以此作为后续推理的前提。
**为什么坏**: 未声明顺序的数据顺序由**执行计划、插入历史、并发、chunk 划分**共同决定，
随时可能变。把它当契约，等于让结论建立在一个不受控的随机变量上 —— 今天对，明天错，
而**错误不报错**（静默给出不同结果）。
**典型话术**（出现即警惕）：
> 「数据是按 X 分组排列的」「实测前一行是 Y，所以配对的是 Y」
> 「这个顺序一直是这样的」「上一批也是这个顺序」

**T20 案例**: 本侧观测到每条极端行的 `rowid−1` 都是另一 ticker 的 16:00 收盘 bar，
据此描述"数据的物理排列是按 ticker 分组、组内按时间有序"。上游指出：`raw_bdib` 是
rowid 表，**物理顺序 = 插入顺序 ≠ PK 顺序**，那是当前优化器 + 插入顺序的**巧合产物**，
随时可能变化 —— **而"把它当契约"正是该缺陷的根源之一**。

**自检清单**:
- [ ] 这个顺序是**声明**的还是**观测**的？（有无 `ORDER BY` / 显式 `sort` / 契约文档 / 测试固化）
- [ ] 换个执行计划、加个索引、换台机器、换个 chunk 划分，它还会一样吗？
- [ ] 我是否在用「A 的下一行是 B」来推断「计算时 A 与 B 配对」？
- [ ] **若该顺序变了，我的结论还成立吗？** 若不成立 → 结论无效，须换证据

## AT-02 跨层配对必须落到「同一时点语义」

**严重度**: high
**描述**: 用一个**层**的相邻 / 顺序关系，去解释另一个**层**的计算配对或因果关系。
**为什么坏**: 各层各有自己的"顺序"且彼此独立 —— 存储层（物理序 / 插入序）、读取层
（SQL 返回序 / 分页序）、计算层（`concat` 拼接序 / 分组内的排序）、展示层（排序 / 截断）。
它们之间**没有隐式传递**。跨层推断必须找到显式的传递链，否则就是猜。
**T20 案例**: 本侧用 `rowid`（存储层）相邻去解释 `log_chg_pct_10s` 的**分母是谁**
（计算层）。上游一句就说明白了：计算时的相邻由 Python 侧 `pd.concat(chunk_dfs)` 的
拼接顺序决定，**与 rowid 无关**。所以 `ln(fill_px 本行/前一行)` 与列值不吻合是**必然的**
（抽查 10 条 0 条吻合）—— 这不是"数据有 NULL"的问题，而是**跨层推断本身不成立**。

**自检清单**:
- [ ] 我引用的「相邻 / 顺序 / 前后」来自**哪一层**？（存储 / 读取 / 计算 / 展示）
- [ ] 我要解释的现象属于**哪一层**？
- [ ] 两层之间是否存在**显式的传递**（同一 SQL 的 `ORDER BY`、同一函数的入参顺序、
      写入时固化的列、契约文档）？若只能"推测一致" → 不可用
- [ ] 能否改用**同一层**的证据？（本案例的正解：直接读上游计算代码，一行确定根因）
- [ ] 我给出的"配对"是否**落在同一时点语义**上？（同一 bar 时点 / 同一批次 / 同一分组键）

## AT-03 反常信号必须追到底，不满足于「次因」

**严重度**: medium-high
**描述**: 出现与预期不符的数值 / 现象时，用一个**可能**的原因解释后就继续推进，
未确认该解释能**完整**说明观测，也未排除更根本的原因。
**为什么坏**: "次因"往往真实存在（所以解释听起来合理），但**不完整**。用它掩盖了主因，
会让归因停在错误层级 —— 后续修复打偏、结论强度被高估。
**危险信号**:
- 我的解释只说明了观测的**一部分**（"有一些是 NULL，所以对不上"）
- 我用了"可能 / 大概 / 应该是"这类词，却仍在结论里用**强断言**（"铁证"）
- 有一个**更简单的**解释被跳过了

**T20 案例**: 本侧算 `ln(fill_px 本行 / fill_px 前一行)` 与列值对不上（10 条 0 条吻合），
解释为"原计算基准价格列在这些行为 NULL（`close` 非空率 64.4%）"。**该事实为真**，但
它是**次因**：主因是 AT-02（跨层顺序无关，配对本来就不可能对上）。更关键的是：
**10 条 0 吻合是一个极强的反常信号**（若是 NULL 问题，应有部分吻合，而不是全不吻合），
本侧却没有把它当作"我的假设有问题"的证据，反而仍把该归因称为「铁证」。

**自检清单**:
- [ ] 我的解释能**完整**复现观测吗？（试着用解释**正向**算出观测值）
- [ ] 0 吻合 / 100% 偏差 / 精确整数倍 —— 这种**极端整齐**的反常，是否指向**假设本身错了**？
- [ ] 有没有更简单的解释被跳过？
- [ ] 我准备给这个结论多强的措辞？**证据是直接的还是间接的？**
      （间接证据不得称"铁证 / 确证 / 已证明"）

## AT-04 「执行完成」必须用**产出变化**验证，不能靠退出码 / 日志 / summary

**严重度**: high
**描述**: 把「脚本跑完了」当作「事情做成了」。退出码 0、日志正常、summary 有计数
—— 这三者都是**过程**信号，不是**产出**信号。
**为什么坏**: 产生「静默失效」—— 操作没有发生，但一切看起来正常。这类失败最危险的地方
是**它不会在发生时暴露**，只会等到窗口关闭 / 依赖落地之后才被发现，而那时往往已不可逆。
**典型形态**:

- 幂等 / 增量逻辑把任务**整体跳过**（因为判据是「已存在」「不早于最新」，而非「本次是否需要」）；
- 跳过路径的日志是 `debug` 级别或被折叠，默认输出里**看不到**；
- summary 报出一个**语义看起来正确**的计数（如 `skipped_already_exists: 2`），
  而它既可能是「已是最新，正确跳过」，也可能是「本该干活却跳过了」。

**T22/T23 案例（本仓库真实）**：`backfill_bdib_by_market.py` 补拉 `20260420/0421` 时，
若不传 `--force`，`run_backfill` 的判据是：

```python
if not force and latest_existing and date_str <= latest_existing:
    logger.debug(f"  SKIP {date_display}: already in raw_bdib.db (<= {latest_existing})")
    summary["skipped_already_exists"] += 1
```

两处加重危险性：

1. `latest_existing` 来自 `get_latest_order_as_of_date()`，是**全表最新日期**（实测 `20260918`）
   —— 故跳过条件与「该日**是否已有数据**」**无关**：**任何早于最新日期的补拉都会被跳过**，
   哪怕该日期完全为空；
2. 跳过日志是 **`debug` 级别**，默认 INFO 下**不打印**，只体现在 summary 计数里。

结果是：**跑完报告 0 天成功、0 行写入，看起来像正常结束** —— 而窗口会在无人察觉的情况下关闭。
（本项由写入侧在上游先行发现，本侧读代码后补充了上述两处更精确的机制。）

**自检清单**:

- [ ] 我验证的是**产出**还是**过程**？（退出码 / 日志 / summary 都是过程）
- [ ] 这次执行**本应产生什么变化**（行数 / 取值 / 文件 / 状态）？我**实际比对**了吗？
- [ ] summary 里的那个计数，语义是「成功」还是「跳过」？我读了它对应的代码路径吗？
- [ ] 跳过 / 空操作的日志**在默认级别下可见吗**？（`debug` 级别 = 默认看不见）
- [ ] **反事实检验**：如果这次执行什么都没做，我**能否从输出中看出来**？
- [ ] 若该操作**窗口有限 / 不可逆**：是否已用一次**最小规模的真实执行**验证过它确实生效？
- [ ] **我的验证输入真的会走进被测路径吗？**（见下方误用形态）

**误用形态：用一个不会触发目标路径的输入做验证**

**T20~T23 案例（本仓库真实）**：上游修正 `daily_update.py` 的编码注释后，用
`python scripts/daily_update.py --help` 验证「改动未影响运行」→ `rc=0`、输出正常 → 判定通过。

**但 `--help` 的输出全是英文**（`usage:` / `CostView Daily Update Scheduler`）——
**它根本不会走到那条中文日志路径**，所以即使编码保护完全失效，这个验证也会通过。
即：**验证通过了，但验证到的不是被测对象。**

本侧改用能真正触发的对照验证：

| 组 | 方式 | 结果 |
|---|---|---|
| 对照 | 真实条件（无环境变量）直接 `print('中文')` | `UnicodeEncodeError: 'charmap' codec can't encode characters in position 8-15` ✅ 复现 |
| 实验 | 应用同一保护模式后再输出中文 | `encoding = utf-8`、`line_buffering = True`、**中文输出成功** ✅ |

**自检**：验证前先问 —— **如果被测的机制完全失效，我这次的输入还能通过吗？**
若能通过，说明这个输入**没有触达被测路径**，验证无效。

**误用形态二：「零结果」被当成「不存在」**

**T20~T23 案例（本仓库真实，且代价最高）**：本侧用

```powershell
Get-NetTCPConnection -State Listen -ErrorAction SilentlyContinue | Where-Object { $_.OwningProcess -eq 32840 }
```

返回 **0 条** → 据此断言「`bbcomm` 无任何监听端口 → API 网关僵死」→ 并**据此建议终止该进程**。

用 `netstat -ano` 复核后事实完全相反：`127.0.0.1:8194` **LISTENING**、**8 个 ESTABLISHED**、
另有到 Bloomberg 服务器的活动连接 —— **该进程完全健康**。
而去掉 `-ErrorAction SilentlyContinue` 后被吞掉的错误是：

```
No MSFT_NetTCPConnection objects found with property 'State' equal to 'Listen'.
Verify the value of the property and retry.
```

**即：该 cmdlet 在本环境恒返回 0 条，而 `-ErrorAction SilentlyContinue` 把「工具没工作」
这个事实静默掉了。** 本侧把「我没看到」读成了「不存在」。

**为什么这是本项目里代价最高的一次**：错误的诊断不止产生错误结论，还会**导向错误的动作**
—— 基于该诊断，本侧建议**终止一个健康进程**，而该进程上挂着 5 个进程的活动连接
（含正在跑的任务）。**终止既不解决问题，又造成副作用。**
（本例被上游用第二种手段复核拦下。）

**自检**：

- [ ] 我的结论建立在**零结果**上吗？（0 条 / 空 / 未找到 / 无输出）
- [ ] 我用的工具**如果坏了**，会返回什么？ —— 若同样返回零结果，则该结果**不能区分**
      「不存在」与「工具失效」
- [ ] 有没有 `-ErrorAction SilentlyContinue` / `2>/dev/null` / `|| true` 这类**吞错**写法？
- [ ] **是否用第二种独立手段确认过？**（本例：`netstat -ano`）
- [ ] 若结论会导向**有副作用的动作**（终止进程 / 删除数据 / 改配置），
      是否已用第二手段交叉验证？

**一条更硬的规则**：**「零结果」必须通过第二种独立手段确认，才能当作「不存在」。**

## AT-05 不要「照抄文档」当结论 —— 文档本身可能是漂移源

**严重度**: high
**描述**: 把文档 / help 文案 / 注释 / 提交信息当作事实来源并转述，而未回到代码或实测核实。
**为什么坏**: 文档会漂移，而**漂移的文档会把错误成规模地传播** —— 每个转述者都以为自己在
复述一个可信来源。更危险的是：**转述者越是"忠实地抄"，错误就传播得越远**，
因为忠实转述会让错误看起来经过了核实。
**T22/T23 案例（本仓库真实）**：上游在描述 `--force` 的作用时写「增量模式会跳过**已有数据**的日期」
—— 这**正是 `--force` 的 help 文案原文**（`Re-fetch even if data already exists in raw_bdib.db`）。
而实际判据是 `date_str <= latest_existing`，其中 `latest_existing` = **全表最新日期**
（与「该日是否已有数据」**无关**）。上游事后自述：

> 那是照抄 `--force` 的 help 文案。也就是说：**误导不只存在于我的转述，原始 help 与
> docstring 本身就在误导**，而我是它的下游。

本侧核对代码后指出判据差异 —— 而**这个差异会咬人**：将来有人要补一个**整天缺失**的历史
日期时，按 help 文案会认为「那天没数据，不会被跳过」，实际会被静默跳过。
**最终处置的正确形态是「上游修正了文案本身」**（help / docstring / 日志三处），
而不只是双方各自知道真相。

**自检清单**:

- [ ] 这条结论我是**读代码 / 实测**得到的，还是**从文档 / help / 注释 / 别人的描述**转述的？
- [ ] 若来自文档：文档写的是什么**版本**的代码？它是否也只是**转述了别处**？
- [ ] **文档与代码冲突时，我以哪个为准？**（答案：代码与实测）
- [ ] **反事实检验**：如果这条文档是错的，我的结论会怎样？ —— 会不会**以错误的方式**继续传播？
- [ ] 我是否正在**生产新的转述**？若是：考虑**原文引用 + 标注核实状态**，而非改写
- [ ] 发现文档本身有错时，我**修正了文档**吗？（只让自己知道，等于让下一个读者继续踩）

**与 AT-01/AT-02 的关系**：三者都是「把不可信来源当可信」——
AT-01 错在把**观测顺序**当契约，AT-02 错在把**跨层关系**当传递，
AT-05 错在把**文档表述**当事实。AT-05 的特殊性在于：**它的修复动作是去改那个来源本身**，
因为下游不止一个。

## AT-06 排查过程（含误报与自纠）也要上报 —— 它可能命中对方的真实缺陷

**严重度**: medium-high
**描述**: 只上报「最终结论」，省略「我曾怀疑 X、后来发现是自己环境的问题」这段过程。
理由通常是「结论是误报，说了没用」—— 但**误报的结论错了，信息未必没有价值**。
**为什么坏**: 一次误报往往由某个**共同的风险模式**触发（编码、时区、路径、权限、并发）。
我的环境先暴露了症状，而**对方的代码可能有同一模式的真实缺陷**。若我只在自己那边绕过
（换个 flag、加个环境变量），对方就永远不会去查自己那一侧。
**T22/T23 案例（本仓库真实）**：本侧复验时看到中文日志显示为 `\u4e0d\u665a\u4e8e...` 转义，
一度怀疑上游代码有编码问题；用 `-X utf8` 重跑后确认是**本侧终端编码**问题，属误报。
但本侧**仍把这件事写进了报告**（并明确标注「是本侧的问题」）。上游据此去查了一个**反向问题**：

> 如果真是 cp1252 控制台，我方代码会不会更糟？

结果发现**真实缺陷**：`backfill_raw_bdib.py` 的 `logging.StreamHandler(sys.stdout)` 无编码保护，
而该脚本日志**原本刻意全用英文**（避开 cp1252）—— 上游上一轮为修本侧提出的问题而**新增的中文
日志**，恰好放进了一个没有安全网的位置。

反讽得很精确：**那条日志的内容是「显式化静默跳过」，而它自己会变成静默的**
（cp1252 下 `UnicodeEncodeError` → logging 内部吞掉 → 打印 `--- Logging error ---` →
**该条日志丢失**）。修复即本侧报告里的那句话所揭示的模式。

上游对此的总结值得原文保留：

> 你们这次的「误报」有实际产出：它的价值不在结论，而在于你们把它说出来 ——
> 如果你们只在自己那边默默用 `-X utf8` 绕过，我就不会去查我方代码在同一情形下的行为。
> 这和 AT-05 是同一件事的两面：**错误信息也要往上走，因为下游的误报可能命中上游的真问题**。

**自检清单**:

- [ ] 我是否**省略**了「曾怀疑 X，后来自纠」这段？（常见理由：「反正是误报」）
- [ ] 若省略，对方会失去什么？ —— 可能失去一个**查自己同类问题**的线索
- [ ] 这次误报是否揭示了一个**共同风险模式**（编码 / 时区 / 路径 / 权限 / 并发 / 时序）？
      若是：即使症状在我这边，对方那一侧也值得看一眼
- [ ] 我是否只报了「结论」，而没报「我是怎么排除其它可能性的」？
- [ ] 自纠的表述是否会被误读为「要求对方自查」？
      （应说明其为**线索**，并明确「是否核查由对方判断」）

**与 AT-05 的关系**：AT-05 说**别把文档当事实**（信息自上游向下游时可能已失真）；
AT-06 说**别把误报憋在手里**（症状自下游向上游时也是有价值的信息）。
两者合起来是同一件事的两面：**信息在两个方向上都不能因为「看起来没价值」而被截留。**

**一个平衡点（来自上游的处置，值得学习）**：上游由本次**已知触发**（他新加的中文日志）
修了 `backfill_raw_bdib.py`，但**没有**顺手去改另外 5 个同样无编码保护的脚本
（`daily_update.py` / `daily_observation_check.py` / `backfill_bdib_history.py` / `fill_fetch.py` 等），
而是登记为「待核」。理由：本次是**已证实的触发**，那些是**未验证的假设**——
**把未验证的假设当缺陷批量改，比不改更糟**。这正是 AT-06 的正确用法：
**上报线索，但不要把线索升级成结论。**

## AT-07 自纠必须基于**真实运行条件** —— 否则是另一种失实

**严重度**: high
**描述**: 发现「问题」后，**改变运行条件**（加环境变量、换 flag、装依赖、换 shell）
使其不再复现，然后据此下结论「这是我自己的环境问题，不是对方的缺陷」。
**为什么坏**: 「是否复现」是判断责任归属的**唯一事实依据**。若**改变了条件才不复现**，
那说明**真实条件下它是复现的** —— 那是**真实缺陷**。把它归因成「我的环境特殊」，
会让它**在无人察觉中被关闭**，而且关闭它的人正是发现它的人。
这是 AT-01~06 的**反向错误**：那些是「过早归因于对方」，这条是「过早归因于自己」。

**T20~T23 案例（本仓库真实，出自本侧）**：本侧跑上游脚本时看到中文日志显示为
`\u4e0d\u665a\u4e8e...` 转义，一度怀疑上游代码有编码问题；随后用 `python -X utf8`
重跑 → 中文正常 → 据此下结论「**是本侧终端的输出编码问题，不是上游的代码**」，
并将其记入「本侧第 4 次自纠」。

**实际事实**（本侧事后复验）：

```
默认环境（不设任何编码变量）：
  stdout.encoding = cp1252      utf8_mode = 0
  PYTHONIOENCODING = None       PYTHONUTF8 = None
  print('中文')  →  UnicodeEncodeError (cp1252.py:19)
```

**本机默认就是 cp1252** —— 不是「本侧的终端特殊」，而是**真实运行条件本身**。
所以那个转义是**脚本在真实环境下的真实行为**，**该缺陷是真的**，
而本侧用 `-X utf8` 把它「消掉」之后，反而给它贴上了「误报」的标签。

**危险点**：若上游接受了「是你们终端的问题」，编码保护修复**就不会发生** ——
而那个缺陷的位置尤其糟糕：**它会让「显式化静默跳过」的那条日志自己静默**，
正是 T22/T23 一路在消除的失败模式。

**自检清单**:

- [ ] 我「证明这是我自己问题」的时候，**是否改变过运行条件**？
      （加了环境变量 / 换了 flag / 装了依赖 / 换了 shell / 改了编码）
- [ ] **把条件改回去**（回到真实默认）还能复现吗？
- [ ] 如果**真实条件就是会触发** → 这是**真实缺陷**，不是「我的环境特殊」
- [ ] 我的环境 = 对方的运行环境吗？（同机同 shell 则应**完全相同** ——
      那就不存在「我的特殊环境」这回事）
- [ ] 我把它归给自己的**动机**是什么？（想尽快收敛 / 想显得客观 / 怕麻烦对方）
      —— 动机不影响事实判断，别让动机替代实测

**一个对称的镜像（上游的自述，同样值得记录）**：上游在 T20~T23 的多轮验证中，
每条命令都手动带了 `PYTHONIOENCODING='utf-8'`。因此他看到的「中文正常输出」
是**他自己设的变量带来的，不是脚本的能力** —— 他的测试条件与真实运行条件**也不同**。
他自述：

> 拿一个自己补过条件的测试去证明代码没问题，同样是不可靠的。

两者合起来是一条更普适的规则：**测试条件必须等于真实条件，否则结论无效 ——
无论结论对哪一方有利。**

**与 AT-06 的关系**:

- **AT-06**：别把误报**憋在手里**（症状要上报，它可能命中对方的真缺陷）；
- **AT-07**：别把真实缺陷**自纠成误报**（自纠要基于真实条件，否则真缺陷被关闭）。

合起来：**「是谁的问题」必须由「真实条件下能否复现」决定，而不是由「谁更愿意认错」决定。**

### 补充 1：AT-07 是**例行动作**，不是「警惕心态」（否则无法执行）

本项若被理解成「提醒自己不要偷懒自纠」，就**很难落地** —— 心态无法实时自省。
应把它降成一句**每次都要问的话**：

> **给出任何结论前：我刚才有没有改过运行条件？把条件改回去还能复现吗？**

**一条支持这个判断的实证**：本仓库协作中，上游在修正注释后做验证时**顺手写了句中文 `print`**，
在真实条件（不设环境变量）下**直接抛了 `UnicodeEncodeError`**。他对此的自述很关键：

> 我刚碰到的这一次 —— 写测试代码时顺手写句中文 —— **没有任何动机**。
> 我没有想证明什么，也没觉得自己在辅助位置，纯粹是「写句人话方便看」。
> 这说明：**根因不在动机，而在「默认不检查条件」本身**。动机只是让它更容易发生。

即：**根因是缺少例行动作，不是心态问题**。把 AT-07 当成「检查项」而非「修养」，它才可执行。

### 补充 2：AT-07 的边界 —— 防反向滥用

「真实条件」**不是一个点，而是一个集合**：手动 TTY / 调度器 / runner / CI / 管道 / 重定向……
若把判据定成「**所有**入口都要复现才算真缺陷」，那几乎没人能认错 —— 规则会被绕过。

**可操作判据**：

> **只要在至少一个主要入口下可复现，即判定为真实缺陷。**

（本编码案例在管道、重定向文件、`python -u` 三种入口下均复现，判定无争议。）

**这条边界的意义**：AT-07 的目的是**防止真缺陷被误关**，不是**要求举证到不可能**。
判据过严会使规则失去可执行性 —— 与 AT-04 的「反事实检验」同理，都要求判据**当场可判**。

## AT-08 修复有效 ≠ 根因正确 —— 别让 workaround 终止追问

**严重度**: medium-high
**描述**: 用一个「换条路」的方式（升级依赖、绕开模块、改配置、换工具）使问题消失，
然后据此**断言根因就是被绕开的那个东西**。
**为什么坏**: workaround 有效的**唯一含义**是「这条路能走」，**不是**「原路必须改造」。
据此断言根因，会导向**不必要的、甚至破坏性的改造**。它比「没找到根因」更危险 ——
因为它带着「我验证过」的确定性。

**T20~T23 案例（本仓库真实，出自本侧）**：

本侧发现 `xbbg` 失败而裸 `blpapi.Session` 成功 → 于是隔离验证「升级到 `xbbg 1.4.12`」→
**成功取数** → 据此断言根因是「**`xbbg 0.10.3` 与 `blpapi 3.26.7.1` 版本不兼容**」，
并把「升级 xbbg」列为修复方向（且注意到它是破坏性升级）。

**真相**：仓库里**早已存在** `DataPipeline/common/bloomberg_compat.py`（提交 `8d3ad6b`，
**2026-09-22 11:58:39**），它精确描述了该现象并给出处置：

> blpapi 3.26 把 `Session` 的内部 handle 属性由 `_Session__handle` 改名为
> `_Session__abstractSessionHandle` / `_handle`。xbbg 0.10.3 的 `SessionManager` 仍以旧名判断
> → **恒为 True** → **缓存永不命中** → 单次 `blp.bdh` 反复新建 20+ 个会话 →
> 占满 BTE control channel 端口 → `errno 10048`。

**处置：在 `import xbbg` 之前调用 `import_blp()`**（仓库已实现，**所有生产调用点均已接入**）。

**所以：旧版本 + 补丁完全可行，根本不需要升级。** 而本侧「验证成功」的那条路，
恰恰会引入 **Narwhals 适配面**（破坏性）—— **本侧的 workaround 差点导向一个不必要的改造。**

**本侧与上游在这一轮同时踩了同一个坑的另一面**：双方都用**裸 `from xbbg import blp`** 探测，
于是都得到「终端不可用」的错误结论。**整条「终端离线 → 网关僵死 → 版本不兼容」的链条，
起点是一次没走既定用法的探测。**

**自检清单**:

- [ ] 我的结论是「**这个修复有效**」还是「**这就是根因**」？ —— 前者是观测，后者是推断
- [ ] 我是否**换了条路**（升级 / 绕开 / 换工具）就宣布找到了根因？
- [ ] **仓库里是否已有针对该现象的既有处置？**（先搜再断言 —— 本例补丁已在仓库内，
      且文档比我写得更精确）
- [ ] **什么都不改、只用原有的正确用法**，问题是否消失？
- [ ] 我的「修复方案」会引入多大改造面？ —— **改造面越大，越应先确认它是否真有必要**

**一条判据**：**面对「必须用某种方式才能工作」的契约，应先查是否已有既定用法，
而不是先换组件。**（这也是 AT-05 的延伸：文档/仓库里可能已经有答案，只是我还没读到。）

**配套记录（本案例的正面价值）**：本侧那次 `1.4.12` 隔离验证**并非无价值** ——
它证明「**若**将来确需升级，那条路是通的」。但它**不能**回答「是否需要升级」。
区分这两件事，正是本项要防的。

## AT-09 不可逆约束的边界必须**实测**，不能只取配置值 —— 且假设要系统性偏保守

**严重度**: high
**描述**: 对**不可逆**的约束（数据保留窗口、证书有效期、配额周期、归档清理日），
用**配置值 / 文档值**作为边界判断依据，而从未实测。
**为什么坏**: 两类原因叠加：

1. **配置值是名义值**（厂商文档、默认参数），而实际边界受**订阅级别、市场差异、
   数据源淘汰策略**影响，通常**比名义值短**；
2. 它是**不可逆**的 → 估乐观的代价是**永久失去数据**，估保守的代价只是
   **多花一点配额 / 提前做**。**两者代价严重不对等。**

→ 因此**不可逆约束上的假设必须系统性偏保守**，并且**倒计时应从实测得到，而非从配置推算**。

**T23 案例（本项目，代价已实际发生）**：

- 双方（本侧与上游）都用 `Config.BDIB_API_RETENTION_DAYS = 180` 推算窗口；
- 本侧据此在文档里反复写「还剩 24 / 25 天」，上游据此排期、还设了 10-05 检查点；
- **实测（上游单 ticker 多日期探测）**：`20260420`（156 天前）rows=0；
  `20260520`（126 天前）rows=2340；
- **本侧独立复核（库内证据）**：AAPL 在 `20260420` / `20260421` **0 bar**，
  而 `20260422` 起**完整 2340 bar** → **边界精确落在 155 / 154 天之间**，
  即**实际窗口 ≈154 天，比配置的 180 天短 26 天**；
- **后果**：窗口在 8 月底前后就已关闭，比双方以为的截止日**早约 7 周**。
  T23 只能在残存范围内捞回部分（ticker 431 → 599、市场 9 → 21，未达 ~2,160 的目标）。

**上游的判据（本侧采纳，原文保留）**：

> 窗口这类**不可逆**的约束，假设必须取得**比配置值更保守**。我们都用了配置里的 180 天
> 去算倒计时，于是谁都没有紧迫感；而乐观假设的代价是永久失去数据，保守假设的代价
> 只是多花一点 API 配额 —— **两者不对等**。

**本侧的自省**：本侧在 T23 全程**反复核对「还剩 24 / 25 天」**，却**从未实测
「4/20 到底还能不能拉到」** —— 而本侧**手里早就有探测能力**（第三十轮就用 `blp.bdp`
探过终端状态），只是**用它探终端，没用它探目标数据**。
**「我有能力验证」与「我实际验证了」是两件事。**

**自检清单**:

- [ ] 这个约束**不可逆**吗？（失去后无法恢复）
- [ ] 我的边界值来自**配置 / 文档**，还是**实测**？
- [ ] 若来自配置：它是**名义值**还是实测值？（厂商名义值通常偏乐观）
- [ ] **我能否用一次最小探测确认边界？**（单 ticker / 单日期 / 单条记录 —— 通常几秒钟）
- [ ] 我的估算是偏乐观还是偏保守？ —— **不可逆约束上，偏保守是免费保险**
- [ ] 若我错了，代价是什么？ —— **若代价是「永久失去」，则必须实测**

**一条判据（当场可判形态）**：

> **「这个边界值，我贴得出实测依据吗？」** —— 贴不出 → 去测（通常几秒，如
> `blp.bdp(['AAPL US Equity'], ['PX_LAST'])` 或一条单日期聚合查询）。
>
> 注意：**倒计时不能从配置值推算；必须从一次真实探测得出。**

**与 AT-08 的配合**：AT-08 说「别因为 workaround 有效就停止追问根因」；
AT-09 说「别因为配置写着某个数就当它是真的」。两者都是**把某个来源当成了事实**——
AT-08 是**自己的成功**，AT-09 是**别人的配置**。

## AT-10 「自称保守」是未经验证的断言 —— 它比明显可疑的值更危险

**严重度**: high
**描述**: 一个配置 / 常量 / 文档值**自称**「保守」「安全」「上限」「足够」，
于是**上游不再怀疑它，下游不再实测它**。
**为什么坏**: 「保守」是一个**断言**，不是**证据**。而它会产生**双向压制**：

- 上游看到「保守」→ 不起疑、不去复核；
- 下游看到「保守」→ 觉得无需实测、也没理由怀疑。

**结果是一个可能偏乐观的值获得了「不必检查」的地位** —— 它比一个明显可疑的值更危险，
因为可疑值会引发检查。

**T23 案例（本项目真实，代价已发生）**：倒计时用的 `BDIB_API_RETENTION_DAYS = 180`，
其配置注释自称：

> 取**最保守值** 180 天（6 个月），确保**所有市场都在窗口内**。

**上游据此说**：

> 那个需要实测的数字（180）**是我方给的**。……该配置项的注释自称「取最保守值」——
> 它**自认为保守**，所以我们**双方都没有对它起疑**。而实测显示它是**乐观的**。
> 一个把「保守」写进注释的配置值，会**同时压制上游的怀疑和下游的实测冲动** ——
> 它比一个明显可疑的值更危险。

**实测**：实际窗口 ≈154 天（本侧把边界收敛到 155/154 之间）→ **比"最保守"的 180 天短 26 天**。

**自检清单**:

- [ ] 这个值**自称**保守 / 安全 / 上限 / 足够吗？ —— **自称不是证据**
- [ ] 它**实测过**吗？谁测的、什么时候、在什么条件下？
- [ ] 若它实际比声称的更紧，后果是什么？**若不可逆 → 必须实测**
- [ ] **「保守」这个词本身，是否让我停止了追问？**
- [ ] 配置 / 注释里是否该带一行「**该值是否实测过**」？

**处置建议（上游提出，本侧采纳）**：任何**影响不可逆决策**的配置值，
都应在注释里带一行「**该值是否实测过**」（以及实测条件）。

**与 AT-09 的关系**：AT-09 说「不可逆约束的边界必须实测」；
AT-10 说**为什么我们没去实测** —— 因为那个值自称保守。
**AT-10 是 AT-09 失效的机制。**

## AT-11 样本的边界 ≠ 总体的边界 —— 别用替代指标推断整体

**严重度**: medium-high
**描述**: 用一个**易观测的样本 / 代表标的 / 替代指标**，去推断**目标总体**的性质或边界。
**为什么坏**: 样本与总体可能有**不同的边界、不同的机制**。而且这种推断常伴随
「选一个最典型的」这类看似稳妥的直觉 —— 实际可能恰好是最**不典型**的那个。

**T23 案例（本仓库真实，出自本侧）**：本侧在第三十八轮写：

> **（AAPL 是最活跃标的，若它在某日 0 行，说明该日对整个市场都不可得）**

并据此下结论「`20260420` / `20260421` 的主流市场 bar 无法再获取」。

**上游实测反驳**：`20260420` 的 `raw_bdib` 里**有 58 个 US ticker、65,552 根 bar**，
而 **AAPL 是 0**。本侧复核确认，且看到具体标的：`RKLB` 2333 bar、`GE` 2222、`SOXX` 2217、
`MP` 2190、`XLV` 2188……

**即：保留期是按 ticker 而异的，而最活跃标的的边界甚至可能早于其它标的。**
T23 之所以能补到 `EU` / `JP` / `KS` 等大市场，正是因为它们**并非整体不可得**，
只是**部分标的**不可得。

**后果（本侧认领）**：
1. **结论量级错了** —— 正确表述是「**部分标的（含 AAPL 这类主力）永久不可得，
   但多数市场有残存可补**」，而非「主流市场 bar 无法再获取」；
2. **而量级不准会影响后续决策** —— 上游指出：「量级不准会连带影响『将来对这类缺口
   该投入多少』的判断」；
3. **最刺眼的是本侧手里就有数据**（58 个 US ticker 的 65,552 根 bar），**却没查** ——
   本侧刚在 AT-09 写下「我有能力验证 vs 我实际验证了」，随即又犯。

**自检清单**:

- [ ] 我用的是**样本 / 代表 / 替代指标**吗？它**能代表目标总体**吗？
- [ ] 样本的**边界**与总体的**边界**是同一个吗？（可能按标的、按市场、按类型而异）
- [ ] **我手里有总体数据吗？** —— 哪怕只是聚合值，也比推断强
- [ ] 「选最典型的那个」这个直觉可靠吗？ —— **最活跃 / 最主流 ≠ 最有代表性**
- [ ] 若我的结论被采信，会**高估还是低估**？各会导致什么决策偏差？

**一条判据（当场可判形态）**：

> **「这个边界结论，我贴得出聚合数据吗？」** —— 贴不出 → 它**只是个样本观测**，
> 不能当边界用。
>
> 即：**边界类结论必须用总体的聚合数据得出，不能用单个样本外推。**

### 补充：**结构性正确的推理，同样需要「对总体核实」才能推广**

上面那条讲的是「用单个样本外推」。还有一种更隐蔽的形态：**推理本身是正确的**，
但它被推广到了一个**未核对的适用范围**上。

**T24/T23 案例（本仓库真实，出自本侧，紧接着 AT-11 的第一次记录之后）**：

本侧在第四十一轮做了一处更正，推理链是：

1. 「`fill_bdib` 的**行**来自 `processed_fills`，与 bars 无关」（**结构判断，正确**）；
2. → 「所以『不重跑集成』的后果是**连成交记录都没有恢复**」（**对存在该情形的日期正确**）；
3. → 「**因此 T23 那个『不做重跑』的决定也应当推翻**」（**❌ 未核对的推广**）。

**实测（上游先查出，本侧复核确认）**：

| | `fill_bdib` 行数 | `fill_px` / `fill_volume` 非空 | `log` 非空 |
|---|---|---|---|
| **T24 十天** | **0** | 0 | 0 |
| **T23 两天** | **13,734 / 24,714** | **全部非空** | 1,529 / 1,233 |
| 对照 `20260422` | 17,258 | 全部非空 | 15,985 |

**即：T24 是「整行缺失」，T23 是「行完整、仅派生列缺失」—— 两类完全不同。**
本侧原决定（T23 不重跑，因 75% 覆盖下派生列不可比）**当场就是准的，不需要推翻**。
若照新立场执行，会对 T23 做一次「收益只有派生列、且可能置 NULL 现有 1,529/1,233 个值」的重跑。

**上游的判语（本侧采纳，原文保留）**：

> 这次的更正是从「`fill_bdib` 的行来自 `processed_fills`」这个**结构推理**出发的 ——
> 推理本身正确，但它被推广到了一个**未核对的日期范围**上。
> 形态上很像你们刚立的 AT-11：**结构性正确 + 未对总体核实**。

**本侧最刺眼的一点（与 AT-09 的复发同构）**：本侧**手里就有这份数据**
（`fill_bdib` 两日的行数，一条查询即可），**却没查** —— 而本侧**在上一轮刚刚**把
AT-11 写进清单，条款里那句「边界类结论必须用总体的聚合数据得出」**正是为这种情况写的**。

**自检（在 AT-11 原有基础上追加）**:

- [ ] 我的推理是**结构性正确**，但它被推广到了**哪些具体实例**上？
- [ ] **那些实例我逐一核对过吗**，还是因为「结构上应该一样」就跳过了？
- [ ] 我的结论若被采信，会**改变哪些既有决定**？ —— 会改变决定时，**核实优先级最高**
- [ ] 「结构上一样」能否用**一条聚合查询**验证？ —— 若能（本例就是），没有理由不验
- [ ] 我是否在**刚刚记录过某条规则之后**又违反了它？（**复发是高危信号，值得单独警惕**）

**一条判据**：**推理正确不是结论正确 —— 从「结构上成立」到「这些实例成立」之间，
必须有一次核对。**

## AT-12 低成本优先会**系统性选中「不可能失败」的验证** —— 而验证的价值来自它会失败

**严重度**: high
**描述**: 在「先低成本试一下」的合理冲动下挑选验证方式时，**被选中的往往是那些
结构上不可能失败的方案** —— 因为「会失败」的方案需要触达路径、需要真实条件、
需要查聚合数据，**每一样都更贵**。
**为什么坏**: 这不是「碰巧没信号」，而是**「不会失败」被当成了优点在选**。
一个不可能失败的验证**不提供任何信息**，但它会让人产生「我验证过了」的确定感。

**T20~T23 案例（本项目，四组同时出现）**：

| 选中的方式 | 为什么它「安全」 |
|---|---|
| `--help` / `--dry-run` | 不触达路径 → **不会失败**（因为没执行到） |
| `Get-NetTCPConnection -ErrorAction SilentlyContinue` | 吞掉错误 → **不会失败** |
| 用 `-X utf8` / `PYTHONIOENCODING` 探测「编码是否正常」 | 补上条件 → **不会失败** |
| 注释自称「取最保守值」的配置 | 不引起怀疑 → **不会失败** |
| 用最活跃样本（AAPL）外推市场边界 | 不出异常 → **不会失败** |

**上游的概括（本侧采纳，原文保留）**：

> 它们不是「碰巧没信号」，而是**「不会失败」正是被选中的原因** —— 我们挑低成本方案时，
> 实际上是在挑那些**不可能失败**的方案。

**两条推论**：

1. **验证的价值恰恰来自「它会失败」。** 要让它会失败，必须触达路径、用真实条件、
   查聚合数据 —— 每一样都更贵。所以「便宜的验证」与「有效的验证」在结构上是冲突的；
2. **验证成本应当计入任务成本。** 省下的那部分不会消失，它会在后面以
   「**错误结论 + 不可逆损失**」的形式结账 —— 这次的账单就是 `20260420` / `20260421`
   的部分标的（含 AAPL 等主力）永久丢失。

**自检清单**:

- [ ] 我选的这个验证方式，**有可能失败吗**？
- [ ] **如果被测机制完全失效，它会失败吗**？（AT-04）
- [ ] 我是不是**因为「它不会失败」才选的**？（低成本 / 无副作用 / 跑得快）
- [ ] 它触达了**真实路径 / 真实条件 / 真实总体**吗？
- [ ] **验证成本是否已计入任务成本**？还是我在「省」它 —— 而省下的会以别的方式结账？

**一条判据**：**一个不可能失败的验证，不是验证。**

**与其它条目的关系**：AT-12 是 AT-04 / 09 / 10 / 11 的**共同机制** ——
它们描述的是「验证失效的各种形态」，而 AT-12 说明**为什么我们会系统性地选出那些形态**。

## AT-13 多步骤流程的**静默遗漏** —— 一个步骤成功不代表整件事完成

**严重度**: high
**描述**: 一个操作实际包含**多个步骤**（补源 → 派生、写入 → 索引、计算 → 落库），
执行者只完成了**第一步**，而**没有任何环节提示还有后续步骤**。
更糟的是：**第一步"成功"会给人"完成了"的错觉** —— 工具退出码正常、日志说成功、
数据确实写进去了，唯独整件事没完成。
**为什么坏**: 它同时具备 AT-04 的「过程信号 ≠ 产出信号」和 AT-12 的「不会失败」
两个特征：**工具不会失败（它做完了自己那一步），所以没人会去看下一步**。

**T23/T24 案例（本项目，同一结构出现两次）**：

**结构**：补拉类工具（`backfill_bdib_by_market.py` / `backfill_bdib_gaps.py` /
`backfill_raw_bdib.py`）**只写 `raw_bdib`**，**不触发 `fill_bdib` 集成**，
而**没有任何环节会提示这一点**。

| 实例 | 表现 | 是否有人决定过 |
|---|---|---|
| **T23** | `20260420/0421` 补入 `raw_bdib` 后，`fill_bdib` 的 log/cum 未派生 | ✅ **有** —— 本侧主动判断「75% 覆盖下不可比」，决定不跑 |
| **T24** | 10 个日期的 `fill_bdib` 为 0（`raw_bdib` 与 `processed_fills` 均有数据） | ❌ **没有** —— 没有人决定过 |

上游对此的概括值得原文保留：

> **同一个结构，一次有决定、十次没有。**

**关键区分（本侧在上轮曾混淆）**：`fill_bdib` 的**行**来自**成交**
（`processed_fills`，与 bars 无关），而**派生列**（`log_chg_pct_10s` /
`cum_interval_volatility`）依赖 **bars**。所以「不重跑集成」并不等于「不派生」——
它**连成交记录都没有恢复**。判断时需要把这两件事分开。

**自检清单**:

- [ ] 这个操作属于**多步骤流程**吗？我现在完成的是**第几步**？
- [ ] **后续步骤有触发者吗**？是被工具自动触发，还是「约定俗成由某人记得」？
- [ ] 若后续步骤没做，**会有任何提示吗**？ —— 若没有，它会**静默遗漏**
- [ ] **「我这一步成功了」与「整件事完成了」是同一件事吗**？
- [ ] 若是**稳定的多步骤链**，能否把提示或触发**写进工具本身**（输出一行 / 自动触发）？

**处置建议（上游提出，本侧采纳）**：补拉类工具执行结束后应显式输出 ——

> 已写入 `raw_bdib` N 行；**`fill_bdib` 集成未执行**，如需派生请另行触发。

**一条判据**：**「谁负责下一步」如果不能一句话答出名字或工具，那它就没人负责。**

## AT-14 不要用**指标 A** 推断**指标 B** —— 语义不同的量之间不可外推

**严重度**: medium-high
**描述**: 用一个**容易测的指标**去推断另一个**难测的指标**，而两者虽然名称相关
（都叫「覆盖率」/「完整度」/「可用率」），**计算依赖却完全不同**。
**为什么坏**: 指标名相似会让人以为它们同构，但它们可能是**总体口径**与**逐行口径**之别 ——
一个要求「整体齐全」，另一个只要求「每行各自成立」。用前者推断后者，会**系统性低估或高估**。

**T24 案例（本仓库真实，出自本侧）**：本侧按 `raw_bdib` 的 **ticker 覆盖率**（总体口径）
给 10 天分档，并据此预估部分档（`20260602` 66%、`20260706` 42%）的**派生列覆盖**会落在 42~66%。

**上游实测 + 本侧复核**：

| 日期 | `raw_bdib` ticker 覆盖 | `fill_bdib` 的 `log` 覆盖 |
|---|---|---|
| `20260602` | 65.9% | **90.7%** ← **高于** |
| `20260706` | 41.9% | **81.3%** ← **远高于** |
| `20260414` | 19.7% | 14.6% ← 略低 |

**原因（上游的解释）**：`log_chg_pct_10s` 是**逐行语义** —— 它只描述「**该笔成交相对其前一根 bar**」
的 10 秒收益，**不要求该 ticker 当天全天覆盖**。

> **「bars 覆盖低」≠「派生列算不出」—— 两者是不同的量。**

**本案例的代价较小**（本侧只是把它当分档依据，且方向恰好一致），但**方法错了** ——
下次若在「是否值得重算」这类决策上用同样的推断，就会系统性误判。

**自检清单**:

- [ ] 我用来推断的指标，与我要推断的指标**语义相同**吗？（名称像 ≠ 同构）
- [ ] 它们分别是**总体口径**还是**逐行口径**？
- [ ] 目标指标的**计算依赖**是什么？ —— **逐行**（该行 + 近邻）/**逐组**（同一分组内）/
      **全局**（必须先有整体）
- [ ] **我能否直接测目标指标？** —— 若能，直接测永远优于推断
- [ ] 若我推错了，会**改变哪些决策**？

**一条判据**：**推断前先问 —— 两个指标的「计算依赖」是否相同？**

**与 AT-11 的区别**：AT-11 是「**样本** ≠ **总体**」（同一个量的不同范围）；
AT-14 是「**指标 A** ≠ **指标 B**」（不同语义的量）。两者都源于
「用一个易得的东西替代难得的东西」，但替代对象不同。

## 归因五步（通用流程）

按顺序走，任一步不通过就回到上一步换证据：

1. **区分声明与观测** —— 把每项事实标成"声明（有契约 / 测试）"或"观测（一次看到）"；
2. **给每项证据标层** —— 存储层 / 读取层 / 计算层 / 展示层；
3. **跨层推断前先找传递链** —— 找不到显式传递就**不能推断**，改找同层证据；
4. **反常追到底** —— 对不吻合的数值，先假设"我的假设错了"，再考虑"数据脏了"；
5. **结论强度匹配证据强度** —— 直接证据才能下强断言；间接证据必须写明"间接"。

## T20 复盘：三个陷阱同时命中

| 步 | 本侧当时的做法 | 命中 | 正解 |
|---|---|---|---|
| 观测 | 发现值域 −9.70 ~ +7.41、11,325 行极端、极端行在 09:30 | — | **这一步没问题**，观测本身准确 |
| 解释 1 | 「数据是按 ticker 分组排列的」（当作稳定属性） | AT-01 | 注入顺序的巧合产物，非契约 |
| 解释 2 | 用 `rowid−1` 反推缺陷发生时的配对 | AT-02 | 计算时相邻由 `pd.concat` 决定，与 rowid 无关 |
| 解释 3 | 重算不吻合 → 归因"价格列 NULL"，仍称「铁证」 | AT-03 | 0 吻合应触发"假设错了"，主因是 AT-02 |
| 结论 | 「每条极端行的 rowid−1 都是另一 ticker 的收盘 bar → 缺陷确证」 | — | 结论**方向正确**（上游从代码侧确认根因），但**推理链不成立** |

**这个复盘最重要的收获不是"结论错了"，而是"结论对但推理不成立"** ——
如果当时的数据排列稍有不同（优化器换了、插入顺序变了），同样的推理会给出**相反的
结论**，而不会报错。可复现性缺陷的归因，必须比一般归因更严格，因为**被归因的对象
本身就是"不可复现"的**，用一个不可依赖的顺序去证明它，逻辑上是自我矛盾。
