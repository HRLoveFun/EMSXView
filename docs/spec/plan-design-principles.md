# 计划设计原则（Plan Design Principles）

> 跨特性可复用规范 —— 任何计划（数据改造 / 优化 / 重构）执行前必读
> 关联：`specs/002-pipeline-guardrail/`（管道护栏，管数据流；本文件管计划流）
> 配套阅读：`docs/spec/anti-patterns.md`（★ 禁止模式）、`docs/spec/boundary-protection.md`（运行时防护）
> Last updated: 2026-08-14

---

## 1. 适用范围

本规范适用于**计划 = 涉及数据库结构 / 数据迁移 / 存储 / 性能优化的变更方案**，如：

- `specs/002-pipeline-guardrail/optimization_plan.md`（数据结构与存储效率优化）
- 任何 Schema 迁移、索引调整、存储引擎切换、数据回填/清理方案

纯前端样式、纯文档类改动不受本规范强制约束（但 G3 充分且必要原则仍建议适用）。

---

## 2. 元模式：计划护栏（Plan Guardrail）

四条原则不是平级口号，而是覆盖 **计划 → 执行 → 验收** 全生命周期的门控链 G0 → G3。
任何计划按同一范式套用，新增原则也按此范式扩展。

**统一范式（每条原则固定字段模板）：**

```
编号 + 短名 → 目的（为什么）→ 判定标准 DoD（怎么算通过）→ 落地手段（怎么做）→ 反模式（禁止什么）
```

**两层抽象：**

- **原则层**：本文件 4 条不变原则，跨计划复用
- **实例层**：每份 plan 把 G0-G3 门控落在自己的问题分层（P0-P5）与"实施注意事项 / 向后兼容"小节中

---

## 3. 原则清单

### P1 数据零受损（安全红线，G0 顶层硬约束）

- **目的**：确立技术方案的统一原则，合理科学改造当前数据库，**不可造成数据受损**。
- **判定标准 DoD**：
  - 改造前有备份 / 回滚方案
  - 改造后行数、字段、日期维度与基线一致（gap = 0）
  - 迁移幂等可重入（重复执行不产生副作用）
- **落地手段**：
  - 迁移脚本 + 轻量备份 + 基线快照对比
  - 参照 `scripts/ops/cleanup_raw_bdib_empty_bars.py` 三道安全闸模式
  - 破坏性操作（ALTER / DROP / VACUUM）需维护窗口 + 空间预检
- **反模式**：
  - 无备份直接 `ALTER` / `DROP`
  - 删除无清单快照（历史教训：57.58 GB .BAK 堆积、archiver 日期列格式错配致整年误删，见 `docs/spec/boundary-protection.md` H1）
  - 迁移不可重入，失败后无法重跑

---

### P2 三性齐备（前置门，G1 每步开工前）

- **目的**：每一步推进要有**理论支持**、**可行技术**、**有效检验**。
- **判定标准 DoD**：每步计划显式列出三栏，缺一不可：
  - 理论依据（为什么这样改是对的）
  - 技术方案（用什么技术、改哪个文件）
  - 检验方法（怎么验证改对了）
- **落地手段**：
  - 步骤模板化，参照 `optimization_plan.md` 的"问题 / 优化项 / 预期收益 / 前置条件"维度表
  - 开工前执行前置验证（如 Q01 需先 `SELECT DISTINCT length(mkt_timestamp)` 确认格式统一）
- **反模式**：
  - 凭直觉改库、无前置验证
  - 只写改动不写检验方法，验收无法对照

---

### P3 全程防漂移（过程门，G2 执行中）

- **目的**：全流程要有**边界监控**、**防漂移检查**，确保执行不变形、不走样、不偏离主线。
- **判定标准 DoD**：
  - 阶段 checkpoint + 基线对比（diff）
  - 范围锁：超范围改动即拒绝
  - 偏差即回退（有明确回退路径）
- **落地手段**：
  - `EXPLAIN QUERY PLAN` 验证索引生效（Q01 防回退）
  - 双引擎对比基线（DuckDB/Parquet vs SQLite，401M 行 diff < 0.0001%，见 Q11）
  - 幂等操作：`CREATE INDEX IF NOT EXISTS` + `DROP INDEX IF EXISTS`
  - 引擎/后端白名单 + 环境变量回退（`BDIB_QUERY_ENGINE=sqlite`）
- **反模式**：
  - 执行中超范围加料（顺手改无关字段）
  - 无 checkpoint 的一次性长事务
  - 引擎切换无回退机制

---

### P4 充分且必要（验收门，G3 收尾）

- **目的**：推进检验对照功能需求验收，确保每一处改动优化**既充分也必要**。
- **判定标准 DoD**：
  - 验收清单对照功能需求（不是对照"能跑"）
  - 每处改动 ↔ 需求一一映射：无冗余项（必要）、无遗漏项（充分）
- **落地手段**：
  - 改动-需求双向矩阵：每个改动可溯源到一个需求，每个需求都有改动覆盖
  - 验收时回归执行相关测试 + 基线对比
- **反模式**：
  - 为优化而优化（金锤 / 镀金）
  - 验收只看执行通过、不看需求是否被满足

## 4. 使用方式

### 编写计划时

1. 按 P1 先声明数据安全红线（备份 / 回滚 / 基线）
2. 每条改动落 P2 三栏（理论依据 / 技术方案 / 检验方法）
3. 执行前定 P3 checkpoint 与回退路径
4. 收尾按 P4 建立改动-需求双向矩阵验收

### 审阅计划时（Code Review）

对照四条原则逐一核对：

| 门控 | 核对问题 |
|---|---|
| G0 P1 | 有备份/回滚吗？会破坏数据吗？迁移可重入吗？ |
| G1 P2 | 每步有理论依据 + 可行技术 + 检验方法吗？ |
| G2 P3 | 有 checkpoint + 基线对比 + 范围锁吗？偏差能回退吗？ |
| G3 P4 | 每处改动都对应一个需求？有没有冗余/遗漏？ |
